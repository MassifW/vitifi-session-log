# A direct sale to an invoiced customer, on "Sign wine out"

Mike (23 Nov 2026, during the cellar trays session): the "Why" list on "Sign wine out" has no reason for a direct sale to
a customer who is invoiced. His example: a returning customer contacted the winery directly and was invoiced through
Xero for her wines.

## Built (on branch `claude/compassionate-kirch-582393`, not on main)

- `supabase/migrations/20261129100000_direct_invoiced_sale.sql`: one row in `stock_reasons` for the first winery, as
  WCD was added (20261029100000): code `direct`, "Sale: direct to customer (invoiced)", kind sale, excise
  home_consumption (an NZ sale), asks who it went to, no country, sort 25 (after the website order, before trade).
  Data only; `on conflict do nothing`.
- Everything that treats a sale by its kind (stock, "Where it went", year-end figures, the excise month, the Xero
  customer's kind-of-sale picker) picks it up with no code change, since the dialog and those reads load the reasons
  from the table.
- `app/lib/depletions.ts`: `INVOICED_REASONS` gains `direct`, so a direct sign-out with no Xero invoice is listed, like
  trade, export and WCD. The headings on the Stock tab's Xero check ("Signed out as a direct, trade, export or WCD sale,
  with no invoice"), its CSV and the manual say so.
- Manual ("How do I sign wine out?"), `docs/bottling-and-stock.md`, `docs/decisions.md`, `docs/open-items.md`.
- Tests: `tests/stock.test.mjs` pins the row's values and that the migration is data only; `tests/depletions.test.mjs`
  the invoiced list.

## Verified

- Migration run twice on a throwaway Postgres 16 container with `winery` and `stock_reasons` rebuilt by hand to live's
  shape (constraints, composite key, a second winery): first run inserts one row for the first winery only, second
  run inserts none. Not a restore of live, so it proves the statement, not live's data.
- `npm test` 2728 pass, 0 fail, 95 live suites skipped (no `.env.local` in this worktree); typecheck and build pass.
- Not looked at in a browser: the dialog reads the reasons from the database, so it shows the new one only once the
  migration is on whatever database the app reads.
