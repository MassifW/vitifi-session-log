The task queued at the end of the last entry. No finished map layer had
ever been drawn: the map built a tile address template by signing a
tile that never exists. Now every tile is fetched by its path, with the
signed-in person's own session, straight from storage.

## The fault, reproduced before anything changed

The unchanged code, built against a local Supabase (all migrations, the
site locations filled in by hand as before, a test owner login, a
2000 × 1500 px test image as an archived original at Pisa). The app's
own **Tile it again** cut it: `done`, 279 tiles, zooms 16–21. Then a
fresh page with the layer finished, as anyone opening the map sees it:

- **0 tile requests** from the browser, **0 tile images** on the map,
  and the panel saying "Shown at 10.2 cm."
- The server log, each time the map opened: `StorageApiError: Object
  not found` — status 400, `statusCode: "404"`, `code: "NoSuchKey"` —
  from signing `16/0/0.png`, the top-left corner of the world.

(Last entry called that a 500. This time the error showed only in the
server log and my listener recorded no failed response in the browser. I
did not chase the difference; it does not change the fault.)

## How storage answers, checked with curl before designing anything

| Asking for | As | Answer |
|---|---|---|
| a tile that exists | the owner | 200, `image/png`, `cache-control: max-age=3600` |
| a tile that does not | the owner | 400 `{"statusCode":"404","code":"NoSuchKey","message":"Object not found"}` |
| a tile that exists | no login (anon key) | **the same 400 NoSuchKey** |
| a tile that exists | an expired, or a garbled, token | 400 `{"statusCode":"404","code":"NoSuchBucket","message":"Bucket not found"}` |

Two consequences drove the design. "Not found" cannot tell a tile that
is not there from one this login may not read. And "Bucket not found"
carries the same 404 but means the sign-in was not accepted — the bucket
is made by a migration and always exists.

## What changed

- **`app/lib/layerTiles.ts` (new).** `fetchLayerTile(path)`: supabase-js
  `storage.download()` from `map-tiles`, as the person signed in; never
  throws; answers tile / missing / failed. `loadLayerTile` looks in the
  phone's held copy first. Its header records why there is no URL
  template (a signature opens one object: a token for one tile gets 400
  InvalidSignature on its neighbour) and why there is no Next.js route
  passing tiles through (the host is metered).
- **`useMapLayers.ts`.** Each layer is now an `L.GridLayer`, not an
  `L.TileLayer` — there is no URL at all. `createTile` fetches its tile
  by path, hands the `<img>` an object URL, and on Leaflet's
  `tileunload` the URL is revoked and a fetch still running is aborted
  (also on layer removal and unmount). The old "the prefix is signed
  once and the template built from it" comment went with the code.
- **A gap is quiet, a failure is said.** "Not found" is a gap. A tile
  that could not be fetched is counted per layer, with its reason, and
  the panel says so under the layer, with **Try again** (redraws the
  layer). "None of this layer could be fetched" only once nothing more
  is on its way. The counts are of tiles on the map now: pan away from a
  gap and the notice goes with it.
- **"Cannot be read at all".** A "not found" before anything of a layer
  has drawn triggers one check: the tile over the middle of the image at
  the layer's widest zoom, which the tiler always cuts
  (`tileAlwaysCut` in `contours.ts`). If that is "not found" too, the
  panel says nothing of the layer can be shown, and that storage gives
  the same answer for "gone" and "not allowed". Cleared the moment any
  tile draws.
- **"Bucket not found" is a failure**, worded "storage did not accept
  this sign-in; signing out and in again should fix it" — treated as a
  gap, a run-out sign-in would have left the map quietly blank, which is
  the fault being fixed.
- **`offlineTiles.ts`.** The cache is keyed by tile path, written as
  `https://tiles.vitifi.invalid/map-tiles/<path>` (the Cache API keys by
  request; `.invalid` is reserved and never fetched). `preloadTiles`
  takes paths and a fetcher, and counts stored / already held / missing
  / failed separately — the old one counted 404s as held tiles and added
  already-held tiles again. Held and release match a layer by its exact
  prefix. Nothing old to migrate: the pre-load arrived in the same commit
  as the signing trick (1aa5b91) and had to sign the same non-existent
  tile before fetching anything, so it never stored a tile anywhere.
- **"Hold on this phone"** runs on the same fetch. Only blocks the layer
  actually reaches are offered, and only the overlap is fetched. How it
  went is said under the button — it used to replace the whole panel
  with a load failure (`setLoadError`), even for "3 tiles could not be
  fetched". A layer coarse enough to stop before zoom 17 holds its own
  finest two zooms instead of offering "0 tiles".
- **`signedLayerUrl` removed.** No callers were left, and a server action
  that signs any path invites the same mistake again.
- **Tests.** `tests/offlineTiles.test.mjs` keeps every original test
  except the two about stripping a token from a URL key, which no longer
  exists; they are replaced by path-key tests with the same point (held
  on Monday, still held on Tuesday). New: pre-loading against an
  in-memory Cache API, gap vs failure in the exact shapes storage sent,
  overlap, zooms held. `tests/mapTiles.test.mjs` (new): the always-cut
  tile is in the tiler's own list for a north-up flight at every zoom, a
  40,000 px mosaic that gets shrunk, and a run flown 20° off north; and
  guards — the tile bucket is named in exactly three files, nothing signs
  a tile path, no route handler or server action touches tiles, and the
  hook revokes and aborts on unload. Checked that they bite: three
  deliberate breakages in `offlineTiles.ts` each turned one test red, and
  the old `useMapLayers.ts` fails three of the guards.

## Found by running it, and fixed

1. **The map only learned which layers were on when the Layers panel was
   opened.** The panel was the only thing loading them, so even with
   tiles fixed a freshly opened map drew nothing. `VineyardMap` now loads
   the visible layers when the map is ready; once the panel is open its
   list takes over; a failed load is said on the map ("Your map layers
   could not be loaded … Opening Layers tries again").
2. **The data saver never applied to layers already on the map** —
   existing layers were only restyled, never rebuilt. They are now
   rebuilt when their zoom cap, zoom range or placement changes. My first
   rebuild removed the old layer before adding the new one; for that
   instant the base map (which stops at 19) was the deepest thing on the
   map and Leaflet pulled the view from 21 back to 19. Seen in the
   browser; it now adds first, then removes.
3. **Only finished layers are drawn.** A layer being re-tiled comes off
   the map, which is what the panel already said ("Nothing is drawn
   until it finishes").
4. Wording: "about 0 MB", "0.0 MB" and "(storage had a fault (HTTP
   503))" fixed.

## Proved in a browser

Headless Chromium against the local stack, each scenario a fresh
browser (an empty cache — another phone):

- **Drawn:** zoom 18, 9 of 9 tiles drawn, all 200s. Zoom 16 (the
  layer's widest): 2 of 2. Zooming in with the button: 20 → asked 20,
  21 → asked 21, 22 → nothing new (21 enlarged). Screenshot shows the
  test image over the map.
- **Cost, at storage's own gateway log:** 9 GET + 9 OPTIONS preflights
  for that zoom-18 view — every new tile is two requests to storage,
  none to the host. Hidden and shown again: 9 of 9 from the browser
  cache. Object URLs: 9 made, 9 let go when the layer was hidden.
- **Gap stays quiet:** three edge tiles taken out of storage → 6 drawn,
  3 blank, three "not found", no notice.
- **Failure is said:** tile requests cut (no connection) → "None of this
  layer could be fetched (no connection to storage), so none of it is
  drawn." → connection back, **Try again** → 9 of 9, notice gone. Half
  the columns cut → "3 tiles of this layer could not be fetched (no
  connection to storage) — there are gaps in it where they belong."
  Storage answering 503 → "(storage had a fault, HTTP 503)".
- **Unreadable is said:** every tile moved away in storage → 0 drawn, 10
  "not found" (9 + the check of the always-cut tile) → "Nothing of this
  layer can be shown: storage has no tile where there is always one …".
  Tiles put back, **Try again** → 9 of 9, notice gone.
- **Hold on this phone:** with two made-up test block outlines, one
  inside the flight and one outside, only the one inside was offered;
  15 tiles held (48 KB), cache keys by path as designed; then **no signal**:
  zoom 19, 9 of 12 drawn from the phone; zoom 17, 2 of 4; **0 requests
  reached storage**. Back in signal, the panel said "2 tiles of this
  layer could not be fetched (no connection to storage)". **Release**
  gave back all 15.
- **Data saver:** "Save data" at 21 → nothing fetched (19 enlarged);
  "Full detail" → view stays at 21, zoom-21 tiles fetched.

## Where I was wrong, or the check was

- My first browser run reported "0 of 0 drawn": that was finding 1
  above (panel-only loading), not the tile fetch.
- My "open at zoom 20/21/22" views all landed at 19: the map opens
  capped at the base map's 19 and the layer that allows 22 arrives
  after. The real app does the same — see "left undone".
- Two counts were polluted by my script, not the app: the gateway log
  is to the second, so requests from just before going offline were
  counted as offline; and one counter was reset after the click it was
  meant to measure. Both re-run clean; the numbers above are the clean
  ones.
- My own new guard first flagged my history comment in `layerTiles.ts`
  (it quotes `/0/0.png`); it now reads code, not comments.

## Left undone, and open

  The storage policies are the same migrations, but the real check is
  Mike opening the map on the laptop and seeing a finished flight.
- **The Layers panel needs signal to open**: its list comes from the

  "Could not load the map layers". Pre-existing; a field-use gap.

  above. Pre-existing; minor.

  in view (`createSignedUrls`) would avoid it at the cost of expiry and
  batching logic. Not done; worth it only if tiles feel slow on a phone.
  Hosted Supabase may send a preflight max-age the local stack does not;
  not checked.
- **Tiles are uploaded with the default one-hour cache**, so after a
  re-tile a phone that saw the old tiles may show them for up to an
  hour. A re-tile from the same original and placement cuts the same
  tiles, so today this only matters once placement can change.

  go. A small leak, outside this task, not touched.
- The browser checks live in scratch space, as last time: Playwright is
