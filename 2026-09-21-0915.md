# 2026-09-21 09:15 — The service-role sweep, and what it found

*Volumes, yields, vine counts, block layouts, composition percentages
and input rates are withheld from this public copy. The findings and
the reasoning are all here.*

Two checks before the first login. Both turned things up; the first
turned up more than the question asked about.

## 1. The service-role sweep

### The application

One call site, and it is the declared one: creating the login behind a
new staff member, because writing to the auth schema is not something a
signed-in person can do. The permission check is made before it is
reached, and — the part that matters — the staff row itself is inserted
through the ordinary client, so the policy is what permits it rather
than the bypass.

Everywhere else in the app uses the cookie-scoped client. A bootstrap
script and the test suite use the privileged key deliberately and are
not request paths.

### But the key is only one of four ways past a policy

Asking only about the privileged key would have missed the rest, so the
sweep was widened to everything that can read past row-level security:

- the privileged key, which bypasses it outright;
- a function declared to run as its owner;
- **a view without security-invoker — the same thing, and it is the
  default**;
- **a table with row-level security switched off, where no policy on it
  runs at all.**

A reporting function now lists all four. What it found:

### Finding 1 — two tables have had no row-level security at all

Both were created in August without it. Every other table in the
project got it in the migration that created it; these two were missed.

Yesterday's migration wrote policies for both **by name** — and they
did nothing, because policies on a table with RLS off never run. A
table with RLS off behaves exactly like a table whose policies permit
everything, and nothing warns.

Confirmed with the public key rather than inferred: both were readable,
and an insert was refused by a foreign key rather than by a policy — a
valid reference would have gone in. One of the two decides which tile
server the map loads from, so a write there points every user's map at
a server of the writer's choosing.

**Three weeks open.** Both now have it enabled, and re-probing shows
nothing readable, inserts refused by policy, and updates against real
rows changing nothing.

### Finding 2 — the whole test harness was callable by the public key

Postgres grants execute on a new function to PUBLIC by default. So
every verification function written in the last two days was callable
by anyone holding the public key, which ships in every page.

One of them matters: it runs as its owner, it writes to the auth
schema, and it inserts a staff row **with whatever role it is passed**.
Called with the public key it got as far as an unrelated constraint,
which refused it for a reason that had nothing to do with
authorisation. That is luck, not a defence.

All six are now revoked from the public and authenticated roles and
granted only to the service role. Re-probed: every one answers
permission denied.

### Finding 3 — a trigger was asking the wrong question

The trigger that stops the winery being left with no active owner ran
as the caller, so it checked *can this person see an owner* rather than
*is there one*. For anyone whose access lets them read the staff table
those are the same answer; for anyone else it refuses a perfectly fine
change with a message that has nothing to do with what went wrong.
Found because it fired on a probe that should never have reached it.

### Finding 4 — my own report cried wolf

The first version of the reporting function compared a Postgres option
to the wrong literal, so it listed all 21 correctly-configured views as
unprotected. A report that flags everything is a report nobody reads,
and it would have buried the two tables above.

### The tests

A new suite asserts: the privileged key is reached from exactly two
files, both on an allow-list with a written reason — and it also fails
if an allow-listed entry stops using it, so the list cannot outlive
itself; every owner-running function is declared with a reason; every
view runs as the caller; **every table has row-level security switched
on**, which is the check that would have caught this three weeks ago;
and the public key can call no owner-running function except the two
that report on whoever is asking.

### One more thing the suite caught, within a minute

The revoke broke the role verification: it called the fixture from
*inside* the role under test, so every role failed at the fixture
rather than at the policy, and the matrix claimed an owner could not
appoint anyone. Fixed by creating the fixture before the role change,
so the only thing measured inside is the operation being tested. The
matrix is unchanged.

### What is left open, and why

Four things, all on the allow-list with reasons: a PostGIS reference
table that is public by nature and whose extension could break if RLS
were forced onto it; two PostGIS catalogue views that describe the
schema rather than the vineyard; and a retired import table that is
deliberately policy-less so it reads as empty to everyone.

## 2. Existing accounts

**There are none, and there never have been.** No accounts, no staff
rows, no login without a staff row and no staff row without a login.

And the harder question — an account created and then deleted leaves
nothing behind. The authentication audit log records signups,
sign-ins, user creations and recoveries; a new summary function
(counts and dates only, never the entries, which hold IP addresses and
tokens) reports **no events of any kind, ever**.

So nothing exists that the owner did not create, because nothing
exists. The self-signup window has been open since late August and
nobody walked through it.

Two caveats, stated rather than glossed:

- a failed sign-in for an address with no account is not written to
  that table, so the emptiness proves nobody succeeded rather than
  nobody tried;
- **self-signup is still on.** Worth turning off — a login without a
  staff row is worth nothing and a test says so, but defence that does
  not rest on one thing being right is better.
