# 2026-09-21 22:30 — The original is the evidence; the map reads tiles

*Volumes, yields, vine counts, block layouts, composition percentages
and input rates are withheld from this public copy. The findings, the
reasoning and the corrections are all here.*

Five refinements to how large map files are handled. Two React bugs
found while doing them, both of which typecheck and build cleanly.

## 1. Every original kept, untouched

New private bucket for originals, with **no update policy at all**.
That is not an oversight — it is the point. Every upload already gets
its own unique name, so nothing ever needs to overwrite anything, and
with no update policy nothing can.

The old overlay bucket is retired to read-only. It was doing this job
under a name that says the opposite — it sounds like the thing the map
draws — and it held nothing yet, so renaming the idea cost nothing
except doing it before something was in there.

Each layer row now points at its own archive: which bucket, the pixel
dimensions, and both resolutions.

## 2. The map reads tiles and nothing else

The fallback that served the whole uploaded file whenever tiles were
missing is gone.

It was the most expensive path in the app — **tens of megabytes of
orthomosaic every time anyone opened the map, against a couple of
megabytes tiled** — and it fired exactly when someone could least
afford it: right after an upload, before tiling had finished, on a
phone, in a vineyard, possibly on mobile data. A layer with no tiles
now shows nothing on the map, keeps its place in the panel, says why,
and its original is still downloadable.

**That makes the old "too small to bother tiling" case wrong.** There
is no other way for the map to show an image, so everything raster is
tiled now however small. Four tiles is a trivial cost; a special case
that serves whole files is not.

### Downsampling, with both resolutions on the label

A file past what a browser will slice (~120 megapixels) is not refused
and not served whole. It is shrunk until it fits, tiled at that size,
and labelled with both figures:

> Shown at 2.4 cm, original 2.0 cm archived.

At a 2 cm ground sample the larger site is past that limit and lands at
2.4 cm on screen; the smaller site is inside it and is untouched.
Someone measuring a row spacing off the screen is measuring the first
figure, which is why both are there and why the panel repeats it on
every layer. Full-resolution tiles wait for server-side tiling, and the
original is sitting there ready for it.

**The check that matters** is that the shrunk copy sits on exactly the
same ground. Tiling a downsampled image with a transform that still
speaks the original's pixels would scale the layer by the downsample
factor — on a 2 cm flight, out by roughly a quarter, and entirely
plausible-looking. The transform is re-expressed for the new pixel
grid, and there is a test that the four corners do not move by more
than half a metre.

## 3. Download original

A button per layer that states the **size before it starts**, and
whether the file is finer than what is on screen. "Download" and
"download 237 MB" are different decisions on a phone in a vineyard. The
signed link carries a download filename, so what lands in Downloads is
recognisable rather than a uuid — this is the button an agronomist or
another piece of software gets the evidence through.

## 4. In the field

**Hold on this phone**: pre-loads a chosen block's tiles at zooms 17 to
19 into Cache Storage. About **71 tiles, 2 MB** per layer per block —
6 at z17, 16 at z18, 49 at z19.

The cache is written **only** by that deliberate action. Caching every
tile anyone panned over would fill a phone with whatever was browsed,
and "make available offline" would stop meaning anything because it
would already be half true. Keys drop the signing token, so a cache
filled on Monday still matches on Tuesday rather than missing
everything while still taking up the space.

**On mobile data** the map stops fetching past zoom 19 — about 0.21 m a
pixel, roughly 85 m across a phone screen — and upscales what it has
instead. Automatic / Save data / Full detail is a control, not a guess.

The two unknowns fall opposite ways on purpose, and there is a test
that says so:

- an unknown connection is **not metered**, so the map fetches full
  detail — being wrong there costs a bit of data;
- an unknown connection is **not wifi** either, so a pre-load of
  hundreds of tiles warns first — being wrong there costs a lot.

The expensive action needs a positive answer; the cheap one does not.

## 5. Storage, with originals counted

Both sites, three flights a year at a 3 cm ground sample, compressed
GeoTIFF in and tiles out:

    seasons   flights/yr   originals     tiles      total
       1          1          0.10 GB    0.09 GB    0.20 GB
      10          1          1.03 GB    0.92 GB    1.95 GB
      10          3          3.09 GB    2.77 GB    5.86 GB

Keeping the archive roughly doubles the bill and costs about three
gigabytes over a decade. That is the entire price of never having to
say "we only kept the tiles". For scale, the hosting plan already paid
for includes 100 GB.

If the drone pipeline writes **uncompressed** TIFF, the same ten
seasons is 12.03 GB — still inside the allowance, and the one figure
worth checking before it becomes a habit.

Egress is the thing to watch rather than storage, and it is the reason
the untiled fallback had to go: a look at a flight is now a couple of
megabytes instead of the whole file, every time.

## The two React bugs

Both typecheck. Both build. Neither is catchable without running the
screen, which is exactly what cannot be done while there is no account
to sign in with.

**One.** A search-and-replace matched twice — Python's `str.replace`
has no count limit by default — and pasted a whole block of hooks
*inside a `useEffect` body*. Perfectly valid TypeScript; a hooks
violation at runtime.

**Two.** Four hooks ended up *below* the map's "where is your
vineyard?" early return. On that path React renders four fewer hooks
than on the other and throws "Rendered fewer hooks than expected". Only
a site with no location recorded reaches it, so it would have sat
there.

A new structural test now catches both. Worth recording: **its first
version missed the real bug it was written for** — it only looked for
returns at the component's own indent level, and the early return in
question sits one level deeper inside an `if`. It passed, I checked it
against the actual bug, it did not fire, and the regex was wrong. That
check is in the file.

ESLint's react-hooks plugin would catch both properly and is not
installed here. This is the narrow version, and it is a heuristic.

## Also found

Two more uncaught promise chains, both in code written this afternoon,
both caught by the silent-failure test rather than by me: a cache
lookup that would have left a permanent hole in the map if it ever
rejected, and a held-tile count. Fixed rather than allow-listed.

A third module could not be loaded by the test runner because it
imported another with no file extension. Two pure functions moved into
a module that imports nothing, so the offline-tiles module has no
relative imports and loads directly. This is the third time that has
shaped where a function lives; it is now a stated rule in those files'
own comments.
