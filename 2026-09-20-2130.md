## 1. The silent-failure sweep

A reconciliation screen read "Nothing to reconcile" for two days while
several lots were flagged. I said I had only checked that one path.
This is the rest of it.

### The shapes found

**27 promise chains with no `.catch`.** A rejection leaves the
component's state at whatever it started as, which is almost always an
empty array, which renders as "nothing here". Three outcomes:

- **Eternal spinners**, where `setLoading(false)` ran only inside the
  `.then`. Eight screens, one of them with two separate instances.
- **False empties**, where a failed query read as a statement about the
  vineyard — "no records yet", "no plan items yet", "no products
  match", "no matching equipment at this site". The two type-ahead
  pickers were worst: an empty result is also the prompt to create a new
  product or a new sprayer, so a failed lookup invites a duplicate.
- **Silent widening.** A scope-resolution helper returned `null` on
  failure, and `null` means "no narrowing" — so a list quietly widened
  to the whole estate and looked like a larger, successful answer.

**Two in the server layer that are worse than a display problem:**

- a unique-filename helper treated a failed bucket listing as an empty
  folder, so the composed path came back as available and the next
  upload would have **overwritten an existing file**. Not knowing what
  is in a folder is a reason to stop, not to assume it is empty;
- the file export skipped anything it could not fetch to a server log
  nobody opening the archive will ever see. This export is what a
  grower being audited hands over, and a silently short archive looks
  exactly like a complete one. It now writes a MISSING-FILES.txt into
  the archive naming each file and why.

### What was done

One shared failure panel, with one sentence: *nothing on this screen is
a statement about X — the figures did not load*. Every loader keeps a
separate error state and renders it. Where a full failure screen would
be heavy-handed the failure is still stated in place: a dropdown says
its list is empty because the lookup failed rather than because there
was nothing; a parcel card says withholding periods could not be
computed rather than implying the parcel is clear.

Every lookup in the area-navigation layer now throws instead of falling
back, with `single()` changed to `maybeSingle()` so a row that
genuinely is not there still returns null. Only a broken query throws.

### The machine checks

The stale column should have been caught the same afternoon.

- One test extracts every literal table/column query and every database
  function call from the app source and runs each against the live
  schema. Proved by reintroducing the original bug: it fails with the
  file, the line, the query and the reason. Anything the extractor
  cannot read fails the run rather than passing quietly, and a guard
  asserts the extractor is still finding things — so a refactor cannot
  make it pass by finding nothing.
- Another fails on a promise chain with no `.catch`, on a database read
  destructured for its data but not its error, and — added after I made
  the mistake twice in one day — on a server-actions file exporting
  anything that is not an async function.

Both have allow-lists that require a written reason. One entry so far.

## 2. The ledger refuses to be edited

The three volume-ledger tables now raise on UPDATE and DELETE.
Documented as append-only for weeks and broken twice anyway, so it is a
trigger now rather than a convention.

One way through: a migration that has just added a column and needs to
populate it can set a session flag for its own transaction. That is not
editing a record — the column did not exist to be wrong. It cannot leak
past the transaction, it is one greppable string, and it does not open
DELETE.

A verification function tries every forbidden edit for real inside
rolled-back subtransactions. All refused; the backfill flag allowed;
the ledger byte-identical afterwards, which the test asserts.

**Already written that way — reported, not rewritten:** two migrations
that updated ledger rows in place, one that hard-deleted a batch of
events, and one of my own from this morning backfilling a column it had
just added.

The core events table is the other append-only one and is **not**
guarded, because two real code paths update a row they have just
inserted to set fields the insert helper does not take. That is insert
completion, not editing history, but guarding it means restructuring
both first. Recorded as the next step rather than done badly.

### Correcting the earlier entry

I wrote that the edited line values were gone from the database and
recoverable only from the source log. **That is wrong.** Each original
is exactly the line as it now stands plus its own loss row, because the
loss was the residual of that same scaling. The method was still wrong;
nothing was destroyed. Both copies of the earlier entry are amended and
the arithmetic is now a test.

## 3. Logins and roles

### What there was before

Nothing. Every table had row-level security enabled and **no policies**,
and every server action used the service-role key, which bypasses it
entirely. The policies could have said anything.

### The shape

A login and a person are separate things. **A login with no active
staff row reads nothing and writes nothing** — which matters, because
the public key ships in every page and self-signup is currently on, so
a stranger can already create a login. That login is worth nothing, and
there is a test that says so.

Five roles — owner, winemaker, cellar, vineyard, read only. Everyone
reads everything; what differs is who writes what. No compartment on
reads, deliberately: the cellar hand needs to know what was sprayed and
the viticulturist needs to know what it turned into. The roles are
about who can make a mistake in which book.

**No delete policy exists on any table.** That is the whole statement,
not a gap to fill later.

### The hole that would have swallowed the whole thing

Every server action now runs as the caller, with a service-role client
kept for exactly two operations, both writes to the auth schema, each
justified at the call site.

**The views would have been a complete bypass.** A Postgres view runs
as its owner by default, so all 21 of them would have read their base
tables as the database owner and handed the rows to whoever asked —
through the exact objects the cellar screens read from. All are now
security-invoker, and the test checks each returns nothing to the
public key.

Event permissions depend on the row: a function maps an event type to a
side of the winery, and an unrecognised type falls to "either" on
purpose — a new event type nobody can write is a new event type that
silently stops being recorded.

### Who entered it

A `recorded_by_user` column on 28 tables, **defaulted by the database
from the request's own token** rather than passed by the application.
An application that has to remember to set the author will forget, on
the row someone later asks about, and a default cannot be spoofed by a
caller. Timestamps added to the four tables that lacked them. The
existing free-text author columns stay: they carry the provenance of
the historical imports, none of which has a login behind it.

### Proving it

A verification function becomes each role in turn — as a NOLOGIN
database role that inherits exactly what a signed-in person has,
carrying that person's token claims — and tries to write to each book.
**No accounts are created**: creating accounts and handling passwords
is not something to delegate, and a role achieves the same proof.
Everything it writes is rolled back, and the test asserts the staff
table is the same size afterwards.

Separately, with nothing but the public key that ships in the browser:
every table and every view returns zero rows, inserting a record is
refused, and appointing oneself an owner is refused.

### The app

A server-component gate: signed in → the app, signed out → the sign-in
screen, and **could-not-tell → a third screen** that says so, which is
part 1's principle applied to the gate itself. The sign-in screen
distinguishes a wrong password from a login with no access from a
deactivated account, because those need three different responses.

A People tab: the list for everyone, role changes and invitations for
the owner. Inviting emails the colleague and they choose their own
password — nobody types it and the app never sees it. A deferred
constraint trigger refuses to leave the winery with no active owner,
which is a state only the database console gets you out of.

### The one thing I could not do

**I have not created any account, so I have not seen a signed-in
screen.** The gate, the sign-out path and every access rule are
verified; the signed-in screens are verified only by type-checking, the
test suite and a production build. A short document and a script are
there for the owner to run; the script asks for the password with echo
off so it never reaches shell history.

Self-signup should also be turned off in the dashboard. It is already
harmless and should still be off.

### Making the three entry forms usable without training

The acceptance criterion cannot be walked without an account, so what
could be done was done by reading the forms as a newcomer would.

The clearest finding: all four entry forms ask **"Recorded by"** as a
required, empty text box — the first thing that needs explaining, and
the one thing the app now knows. All four pre-fill it from the
signed-in name, with a line saying to change it only when entering
someone else's work. One related field is deliberately left blank: the
person who operated the machine is often not the person typing, and a
wrong name there is a compliance problem rather than an untidiness.

Four controls had no label of any kind; all four now have one.

## 4. Offline parity

The offline queue is now one generic module with the storage key and
the reference function passed in. The harvest screen keeps its exact
public API and its original storage key, so anything queued on a phone
yesterday still sends. The cellar screen gets the same mechanism.

The cellar entry screen gained the whole pattern: an offline banner, a
held count, automatic resend when the signal returns, a send-now
button, and a save path that queues rather than loses — and refuses to
clear the form if storage itself refuses, because an entry the crew
believes is held and is not is the one outcome worth preventing.

A session queues as one draft, and the save is idempotent per source,
so a session that half-landed before the connection dropped resends
only the half that did not.
