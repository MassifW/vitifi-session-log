## Going live: where the plan met the screens

- A `production` branch, which the host deploys; `main` stays where work
  lands, and moving `production` is a deliberate release (each costs 15
  of the free plan's 300 monthly credits).
- The import screen offered `main`; changed to `production`.
- **Environment variables**: the setup screen takes one group with one
  "secret" box, and per-variable scopes are a paid feature. All five went
  in unticked — the two public ones must never be marked secret, because
  Netlify fails a build that ships a secret value and those ship by
  design — and the three server-only ones were marked secret after the
  first deploy, which needs no redeploy. Values went from the Supabase CLI
  and the laptop's settings file onto the clipboard by a script that
  prints only names; nothing was typed, shown, or pasted into a chat.
- Supabase's new publishable and secret keys were **tried against the
  hosted project before they went in**, and the build output was searched
  for the server-only values (none) before they were marked secret.
- **The first deploy answered HTTP 401**: new Netlify teams get private
  projects by default, behind a Netlify login. An invited colleague could
  never have passed it. Fixed: production public, previews private.
- Netlify injected a **"Powered by Netlify" badge script** into every
  page — on by default for free projects since 19 August 2026, drawn in
  the bottom-right corner, over the app's buttons on a phone. Turned off.
- Branch deploys and deploy previews off (under "Developer settings" in
  this Netlify, not where the plan said).
- The project was renamed until it carried only VITIFI's name:
  **https://vitifi.netlify.app**. The Supabase redirect list, which turned
  out to be **empty** (laptop links had only worked because localhost was
  the Site URL), now names the live address and localhost; each name the
  rename released was removed at once, since anyone could claim it and be
  sent sign-in links. Both are confirmed refused.

## `check:live` read nothing on its first live run

It reported the page and zero scripts read, and "no public key found
either" — so it refused to vouch for anything, as designed. On Netlify
every script address ends in `?dpl=<deploy>` (skew protection), and its
pattern required `.js` then a quote. Fixed with a test in the exact shape
Netlify serves; it now reads the page and 13 scripts.

## Backups: four runs

The nightly job backs up the database, restores it into a brand-new
scratch Supabase on GitHub's machine, and compares the two.

1. **Password refused** — a saved copy was out of date. Reset. The
   dashboard's Copy button failed inside the app's browser pane, so a
   random password was generated on the laptop straight onto the
   clipboard, pasted where it was needed, and the clipboard emptied.
2. **Restore refused**: `column "lifecycle_configuration" of relation
   "buckets" does not exist`. The scratch copy ran the CLI's default
   storage service (1.70.3); live runs 1.77.5 — Supabase upgrades on its
   own schedule. A new script reads live's storage version from the
   public `/storage/v1/version` each night and pins the scratch copy to
   it. The backup doc had claimed the scratch copy ran "the same images a
   new hosted project runs"; corrected. (Pushing the fix needed GitHub's
   `workflow` permission for the laptop's login; Mike approved it.)
3. **Restore succeeded; comparison failed** on four sign-in tables that
   live's newer auth service has and the scratch copy's does not — all
   empty. The comparison already treated columns only one side has as a
   note for Supabase's own tables; an empty table is the same case. Now a
   note; a missing table with rows, or any table of the app's own, still
   fails.
4. **Passed.** 49 MB of the free plan's 500. The failure issue opened on
   run 2 closed itself.
