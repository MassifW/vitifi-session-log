# LINZ answering 400: the key has lost its feature-service access

18 November 2026. Mike: "Yes, look into it" (the new failure in the release gates the night before).

**Found.** `tests/property-boundary.test.mjs`, "LINZ answers for a point", gets 400 with "Feature type :layer-50772 unknown".
- A made-up key gets the same answer, word for word.
- LINZ's list of layers (WFS GetCapabilities) for the real key holds no layers, the same same answer as for a made-up key.
- A LINZ Hillshade tile comes back 200 with the real key and 403 with a made-up one, so the key is valid; it has lost the feature-service (WFS) access the land titles need and kept its tile access.
- The suite last passed against live, LINZ included, on 12 Nov, so the change came between 12 and 17 Nov. Not in our code (nothing LINZ changed). Whether LINZ changed how keys are scoped, or the key was edited, is not known.

**Consequence.** If live uses the same key (presumably), "Add a property boundary" cannot read titles on live. Not tried in a browser.

**Fix (Mike's, not code).** On the LINZ Data Service, API keys: give the key WFS access again, or make a new one with it, then `.env.local` and Netlify's environment, then a release.

**My mistake.** One probe cut LINZ's answer at 1,500 characters before scrubbing the key out, and the cut fell inside the key: its first three characters were printed in tool output on this Mac. Nothing was sent anywhere. After that, only counts and status codes were printed. Scrub first, then cut.
