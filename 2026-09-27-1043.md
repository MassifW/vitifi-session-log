# 2026-09-27 10:43 — Going live for nothing: a host, a sender, and backups that restore

*Volumes, yields, vine counts, block layouts, composition percentages
and input rates are withheld from this public copy. This entry is about

Four asks: find the cheapest host that genuinely allows a business to use
it; stay on Supabase's free plan safely, with nightly backups that are
proven to restore; recommend an email sender for the Kahiwi domain; and
deploy. The first three are done as far as they can be without Mike's
logins. **Nothing was created on any account**: the host waits on Mike's
yes, the backups on two GitHub secrets, the email on his GoDaddy login.

This was a cloud session. It could not see Mike's `.env.local`, and —
found early — **its network proxy carries no raw database connections**,
so the live database could not be dumped from here even with a password.
That shaped the whole design: the real backups run in GitHub Actions.

## Hosting: Netlify's free plan

Vercel Hobby is non-commercial. **Netlify's Self-Serve Subscription
Agreement** (last updated 1 October 2025) governs every Netlify plan,
including what it calls the "Free Usage Tier" (sections 5.1, 6, 11.2),
and its grant of use, section 2.2, is *defined* as business use:
"solely for Customer's internal business purposes". The website Terms of
Use (26 March 2026) defer to it for the services.

Checked against this app, not assumed:

- Next.js 13.5 "up to the latest stable", App Router, server actions and
  middleware (as edge functions) all listed as supported. This app's
  Next 16 is inside that on paper; the first deploy is the test.
- **Functions run in Ohio on the free plan** — choosing Sydney is Pro and
  up. The database is in Sydney, so every server action crosses the
  Pacific; estimated half a second to a second more per action. Not
  measured.
- **300 credits a month, then every site on the account pauses** until
  the month turns; the free plan never bills. Production deploy 15,
  compute 10/GB-hour (functions are fixed at 1 GB, so wall-clock time is
  the cost — and Ohio waiting on Sydney is wall-clock time), 2 per 10,000
  requests *including static assets*, 20/GB bandwidth. Branch deploys and
  previews free. My estimate for a handful of users: 25–50 a month plus
  15 per release. Assumptions: ~250 sessions a month, ~30 actions each,
  ~0.8 s per action. **An estimate** — the first month's usage page is
  the measurement.
- Hence **releases are deliberate**: Netlify deploys a `production`
  branch, `main` never deploys. CLAUDE.md now says so.
- 60-second and 20 MB streamed-response limits: the "export everything"
  ZIP will fail once drone originals are stored.
- Section 6.1: free projects can be removed "without notice at our sole
  discretion". Said plainly in going-live.

Also checked: **Google Cloud Run** does have a free tier in Sydney that
allows business use, but needs a card, applies the free tier at Tier 1
prices to a Tier 2 region, charges for stored build images past 0.5 GB,
and cannot map a custom domain in `australia-southeast1` (domain mapping
is a preview in ten other regions; the alternative is a load balancer or
Firebase Hosting in front). Rejected for moving parts, not price.
Cloudflare's free tier needs the OpenNext adapter — rework, excluded by
the brief. Cheapest paid steps: Netlify Personal US$9 (still Ohio), then
Netlify Pro or Vercel Pro US$20 (Sydney).

The client bundle was measured: 1.6 MB of JavaScript, 0.5 MB compressed,
all chunks — bandwidth is a rounding error.

**Found while costing it:** `LayerPanel.tsx` polls every 4 seconds while
any layer is `running`/`pending`, and nothing ever marks an abandoned
tiling job as stalled. One Map tab open all day against a stuck layer is
~7,200 server actions a day — the month's credits in about two weeks.
Queued as its own task, not fixed here.

## Backups

Built: `scripts/backup/` (backup, restore, fingerprint, checks, prepare,
db-url, github), `.github/workflows/nightly-backup.yml` and
`restore-backup.yml`, `docs/backups.md`, 47 tests.

Every night: fingerprint the live database, run Supabase's documented
three dumps with the pinned CLI (2.116.0), write `extras.sql` and the
migration history, fingerprint again, and refuse a dump that is not the
database. Then restore it into a **brand-new scratch Supabase on the
runner** (`supabase init` + `supabase start`, the images a new hosted
project runs), compare, keep it as an artifact, prune to the newest 30
verified, report free-plan headroom, and open or close an issue that
@-mentions Mike.

### How it was proved

No live connection, so the first proof was local. Docker's daemon was
startable in the container. A local Supabase was built from this repo's
migrations: **157 of 168 apply from scratch; 11 fail**, all data imports
(see "The migrations are not a backup" below). Then fixtures: two logins
with real sign-ins (so sessions and refresh tokens exist to be left out),
an invited login that never chose a password, three stored-file records,
staff rows, a ledger correction (and the ledger still refused an UPDATE),
and 168 rows of migration history.

Backed up with the real scripts, restored into a separate brand-new
local project on other ports with the real `restore.sh`:

- **fingerprints matched — "Is the restored database the backup: passed,
  nothing to report"**: every table's rows and content hash; columns,
  constraints, indexes, RLS flags and grants on all 43 of our tables; 131
  policies including the 5 on `storage.objects`; 24 triggers; 50
  functions with their grants; 21 views with `security_invoker`; default
  privileges; extensions; migration history;
- **13 behavioural checks through the restored project's own API**: the
  test owner signed in **with the password set before the backup**; a
  wrong password and the never-set-up invitee were refused; the owner read
  staff through RLS and the public key read none; four sensitive functions
  refused the public key (`42501`); storage policies let the owner see an
  original's record and the public key nothing; **the file itself did not
  come back (HTTP 500)** — the honest limit; the ledger refused an edit
  (`23001`);
- the restore refused a database that already had VITIFI tables.

Then the nightly job's steps were run **verbatim** in the container — the
mask step, the backup step, a fresh `supabase init --force` +
`supabase start` on the default ports, the restore, the headroom step —
and passed. `actionlint` and `shellcheck` are clean. The tests were
mutation-checked: dropping the function-grant comparison and the policy
comparison from the checker turned exactly the two "FOUND 27 SEP" tests
red.

### What Supabase's documented restore gets wrong for this app

Found by the drill, in this order:

1. **The schema dump excludes `auth` and `storage` entirely.** The five
   file-access policies on `storage.objects` do not come back: every file
   record returns and nobody can open a file. Supabase's guide does say
   storage policies "must be manually restored". Fixed by `extras.sql`,
   generated from `pg_policies` with an empty search path so every
   function is schema-qualified.
2. **The documented restore stops on its own roles file**, line 18:
   `GRANT SET ON PARAMETER "log_min_messages" TO
   "supabase_realtime_admin"` — `permission denied for parameter`. The
   CLI filters platform grants of other kinds, not this one. Not in
   Supabase's guide as far as I read. `prepare.mjs` skips grants to the
   CLI's own list of reserved roles.
3. **Every function this app closed to the public key comes back open.**
   A Supabase project's default privileges grant every new function in
   `public` to anon, authenticated and service_role; `pg_dump` writes
   grants relative to Postgres's own defaults. Ten functions, including
   `verify_make_test_staff` (SECURITY DEFINER, inserts logins and staff
   rows with any role) and `auth_activity_summary`. **Watched it happen**
   rather than inferring it from a grants listing: after the documented
   restore, the public key got **HTTP 200** from `security_surface` —
   which itself listed "callable by anon: auth_activity_summary" — and
   from `auth_activity_summary`. `extras.sql` now revokes from everyone
   the platform grants to and re-grants exactly the source's ACL for all
   114 of our objects; afterwards, `42501`. Not in Supabase's guide.
4. Migration history is not in the dump (documented). Dumped separately
   with the CLI's own `--schema supabase_migrations`.
5. After a restore, PostgREST's schema cache is stale (`PGRST202`) —
   `restore.sh` now sends `notify pgrst, 'reload schema'`.

### Decisions, with the reasons

- **Where they live:** GitHub Actions artifacts in the private repo.
  Private to people with repo access, free, 90-day hard expiry. GitHub
  Free: 500 MB storage, 2,000 minutes — both measured nightly.
- **Newest 30 *verified*.** Pruning runs only after a fully good night,
  so a string of failures never deletes the last good copies; a night
  whose drill failed is kept as `…-UNVERIFIED` and never counted.
- **Live sign-in state left out** (sessions, refresh tokens, one-time
  tokens, MFA challenges, flow state, OAuth codes, passkey challenges):
  a backup holding them could be used to act as someone signed in.
  Logins and password hashes stay, so passwords work after a restore
  (proved). Sign-in history (`audit_log_entries`) stays — it is audit
  evidence, and `auth_activity_summary` reads it.
- **Not encrypted.** A passphrase Mike could lose makes every backup
  useless; access control is the repo's. Revisit if the collaborator list
  grows.
- **Failure is loud:** the job opens "Nightly backups are failing" and
  @-mentions the owner; a later good night closes it. If the secrets are
  missing, the issue says "not set up yet" and where the steps are.
- **Two secrets, not one.** Mike pastes the session-pooler string with
  `[YOUR-PASSWORD]` still in it, and the password separately;
  `db-url.mjs` percent-encodes it (a `@` or `#` in a password otherwise
  breaks the string silently), masks the encoded form in logs, and
  refuses the direct connection (IPv6 only, unreachable from GitHub) and
  the transaction pooler, each with a sentence saying what to copy
  instead.
- **Headroom** warns at 60% and opens an issue at 80%: database, storage,
  largest single file (the 50 MB free upload cap), the backup's own
  nightly egress, and GitHub artifact storage.
- A one-click **restore workflow** into a new project: refuses the live
  project (by project ref) and any non-empty database, requires the new
  project's ref typed as confirmation, verifies checksums first, restores
  in one transaction, and checks the result the same way.

### The migrations are not a backup

`seed_sites_blocks_parcels` creates parcels with IDs generated on the
day; ten later migrations name the IDs the live database happened to
generate. Replayed, some fail (`backfill_phenology_2021` first) and some
**succeed while changing nothing**: `backfill_parcel_vine_counts` runs 30
updates `where id = '<an ID that no longer exists>'`, matching no row,
with no error. Two constraints then fail because the data they assume is
missing (`sites_location_required`, `equipment_site_scoped`). The nightly
dump is the only complete copy of the data.

## Supabase: staying free, and the date nobody mentioned

Free: 500 MB database, 1 GB storage, **50 MB per uploaded file**, 5 GB
egress, pause after a week without database activity (the nightly backup
is that activity), no backups. Supabase's terms, like Netlify's, grant use
"limited to Customer's internal business purposes" — no separate rule for
the free plan.

**Pro becomes necessary at the first Pisa drone flight at 3 cm or finer**
— about 80 MB as one GeoTIFF, past the 50 MB cap (Clos Miki at 3 cm,
about 32 MB, fits; either at 5 cm fits). That arrives all at once. The
nightly job's egress is 30 × the dump size a month, and is reported.

**Found: Supabase retires the legacy `anon` and `service_role` keys "by
the end of 2026"**, and says new projects — including projects restored
since 1 November 2025 — no longer get them. So the live app must change
keys within three months, and a disaster restore would only offer the new
kind. Tested today, against a local Supabase with the app's own locked
library versions (supabase-js 2.116.0, @supabase/ssr 0.12.7): with a
**publishable** and a **secret** key, 10 of 10 — sign-in, RLS reads,
storage list and signed URL, harness refusal, the `@supabase/ssr`
server-side `getUser`, and the admin `generateLink` / `updateUserById`
the People tab uses. `check:auth` passes with either key type. So
going-live now says: put the new keys into Netlify from the start. Not
tried against the hosted gateway; the first live sign-in is that test.

## Email: Resend's free plan

DNS looked up rather than assumed. `kahiwi.co.nz` — the domain the code's
own examples use (`vitifi.kahiwi.co.nz` in `tests/authLink.test.mjs`),
**assumed to be the winery's, not confirmed** — has its DNS at GoDaddy
(`ns77`/`ns78.domaincontrol.com`), mail on Microsoft 365 bought through
GoDaddy (MX `kahiwi-co-nz.mail.protection.outlook.com`, the
`NETORGFT…onmicrosoft.com` tenant pattern), SPF `v=spf1
include:secureserver.net -all`, no DMARC, and an A record at GoDaddy's
website hosting. (`kahiwi.nz` and `kahiwi.com` exist too, at other
providers; not investigated.)

Resend: free, 3,000 a month, 100 a day, first on Supabase's own list, and
it has **Auto Configure for GoDaddy** via Domain Connect. Sending domain
`vitifi.kahiwi.co.nz`, so every record sits under `vitifi` and the office
mail and root SPF are untouched. Resend's own Supabase guidance: turn off
click and open tracking (link tracking corrupts one-time links), use a
subdomain, add DMARC. The SMTP values and the manual records are in
going-live, section 3.
