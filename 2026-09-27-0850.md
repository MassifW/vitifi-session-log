## What was actually wrong with the invitation

Mike invited a vineyard-role account from the People tab — his own second
address, "mike as vineyard hand", for the walk. The link landed on
`localhost:3000/#access_token=…&type=invite` and showed the sign-in page.

Two separate faults, and the second was not the one I first described:

1. **Nothing read the link.** The browser client runs PKCE. An invitation
   made by the admin API can only arrive by the implicit flow, tokens in
   the fragment. supabase-js 2.116 rejects that combination as "Not a
   valid PKCE flow url" and returns the error to nobody. Confirmed by
   reading the installed `GoTrueClient._initialize`.
2. **Why sign-in then said "Invalid login credentials".** I first wrote
   — in code comments and a migration — that there was *no password to
   check*. **That was wrong.** Following an invite link makes GoTrue give
   the login a random 64-character password of its own when it has none
   (`signupVerify`). The real account, invited 19:10, link followed 19:11,
   untouched since, holds a 60-character bcrypt hash. So there was a
   password; nobody knew it. The wrong belief cost a feature a rebuild —
   see "Resend invite" below — and the comments now say so.

And one fault in configuration: the Site URL is `http://localhost:3000`,
and the invite passed no redirect, so Supabase used it.

## The flow now

- **One reader.** `app/lib/authLink.ts` parses four link shapes (implicit
  tokens, token_hash, PKCE code, error). `AuthLinkGate` strips the token
  from the address before anything is awaited. The browser client is set
  `detectSessionInUrl: false` so nothing races it.
- **"Choose your password"** — password, confirm, show-what-I-type, save,
  into the app, after checking the login actually has a staff row.
- **A dead link** says "expired or already been used" (Supabase uses one
  code for both, so it does not pretend to know which) and names the next
  step. Every link the app sends carries `?link=invite` or
  `?link=recovery`, which Supabase preserves through its redirect —
  verified against the hosted project — so the dead-link screen knows
  whether to send someone to the owner or to "Forgot your password?".
- **Forgot password** on sign-in, same screen. Reset emails are sent with
  the *implicit* flow on purpose: PKCE ties a link to the browser that
  asked for it, and someone who has lost a password is the person most
  likely to open the email on a different device.
- **Every invitation opens the address it was sent from**, and the People
  tab says what that address is before sending — amber for anything that
  is not a public https host.
- **Resend invite** for anyone invited who has not chosen a password.
  Supabase refuses a second *invitation* to a confirmed address, so for
  someone who followed their first link the resend is a reset email
  landing on the same screen; the owner is told to warn them.

## Two bugs found by running it, not by the tests

Both in `staff_login_state()`, the owner-only function behind Resend.

**`search_path = ''`**, the textbook setting for a SECURITY DEFINER
function, broke it for owners — the only people it answers. It calls
`can_manage_staff()`, whose body calls `current_staff_role()` without a
schema, and a pinned path holds for everything called inside. 42883 on
the People tab. The anon probe had passed, because the public key is
refused before the function runs. Fixed to `public, pg_temp`, the
convention every other definer here uses.

The People tab, notably, did the right thing while broken: "Could not
check who has finished setting up their login — that is not the same as
everyone being set up." That is the failure state earning its keep.

**`encrypted_password <> ''` does not mean "chose a password"** — see
fault 2 above. And the verification I had written *passed*, because its
fixture inserts logins with an empty password: the same wrong assumption
as the code. A test that shares the code's assumption agrees with the
code, not with Supabase. Now:

- `password_chosen_at` is stamped in the login's metadata **in the same
  request** that sets the password, so the two cannot disagree; a
  successful password sign-in stamps it too;
- a login is waiting only if it was *invited* and has no stamp;
- `verify_mark_invited()` makes fixture logins the way an invitation does,
  and `verify_staff_login_state()` checks, as every role, that only the
  waiting invitee is flagged and only an owner sees anything.

Live, as Mike: "mike as vineyard hand — Has not chosen a password yet",
with Resend invite; Mike's own row clear.

## The adversarial review

Three reviewers, independent lenses — security, React and flow, Supabase
library behaviour against the installed source. 22 findings. The two
high ones were the two bugs above, found independently from GoTrue's
source; the reviewer named the `signupVerify` mechanism I had only
inferred. Of the rest, all fixed except one, which is documented:

- session saved before any password existed, so a reload skipped the
  screen for good → a login still owing a password is now **held on
  "Choose your password" by the server**, every load;
- **Next's router wrote the token back.** Next patches
  `history.replaceState` in a `useEffect`; the strip ran in a layout
  effect, before the patch existed, so Next kept the original address.
  Reproduced before fixing: after a dead link, one filter change put
  `?link=invite` back in the bar. Fixed with a second `replaceState(null,
  …)` after Next's patch is in; re-run shows the address stays clean;
- **any `#access_token` fragment silently replaced whoever was signed
  in** — a staff member could plant their own session in the owner's
  browser, and every record after would carry their name. Now asks
  first; verified in the browser with a fabricated token for a made-up
  address while Mike was signed in: it stopped, named both, and "Stay
  signed in" left Mike exactly as he was (server-side too, after reload);
- refresh token from the address never rotated → rotated immediately;
- a dropped connection shown as a dead link → "Could not reach the
  sign-in service" with Retry, the token kept in memory;
- **attacker-written text from the address displayed on the real page** —
  the dead-link screen quoted `error_description`. Now fixed wording only;
- the 30-second per-address cooldown reported as "the hourly allowance is
  used up" (same code, only the message differs) → message read first;
- password saved, then a failure brought the form back, and saving again
  hit "same password" → a saved password never shows the form again;
- "Choose a *new* password" to someone who never had one; stale Resend
  buttons beside a banner saying none were shown; the origin notice
  missing LAN addresses and the allow-list fallback;
- an invitation to an address that already had a login (made by self
  sign-up while signups are on) kept the stranger's password and got a
  staff role → refused, with the reason.

Not fixed: mail scanners (Safe Links and the like) can spend a one-time
link before the person clicks. Documented, with the email-template change
that answers it — the app already reads that form.

The silent-failure test also caught one of mine the same afternoon: a

And the service-role test allow-listed by *file*, so my second
