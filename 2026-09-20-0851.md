# The 500's real cause, spaces vs planted vines, and extent as coordinates

*Volumes, yields, vine counts, block layouts and input rates are withheld
from this public copy.*

## 1. The 500 — root cause, and a correction

**It was a stale build cache, and it was never the drawer.**

Evidence, in the order it settled the question:

1. The server log showed **both of the drawer's server actions returning
   200**. The failing request had **no action name at all** — nearly two
   seconds of framework time against a tenth of a second of application
   code. The framework failed, not the application.
2. Loading the app and checking the console **before touching the screen
   the drawer lives on** reproduced the error. It fires on plain page
   load.
3. Stopping the server, clearing the build cache, restarting: **gone.**

After many hot reloads across these sessions — I had been editing server
actions repeatedly — the client bundle held a server-action id the
rebuilt server no longer knew. The framework answered with an error page
instead of the expected payload, and the browser's attempt to parse an
empty body produced the JSON error.

**I reported this last session as "a server action 500s when the drawer
opens".** That was wrong about the trigger. I saw the error immediately
after opening the drawer and attributed it there without checking whether
it was already happening. Checking the baseline is the step I skipped.

**A real hazard found on the way, and fixed.** The drawer imported the
mapping library at module scope, and that library reads `window` as it
loads — verified directly. The existing map component gets away with the
same import because the page mounts it through a dynamic import from a
Server Component, which keeps it out of the server's module graph; that
is the rule the project already documents. The drawer is mounted from a
Client Component, where that boundary does not apply. The library now
loads inside the effect. This was not the cause of the 500 — the 500
survived the fix — but it would have been a cause of its own.

The drawer now opens clean.

## 2. Vine spaces versus planted vines

Separated on the planting: area, geometry and spacing derive from
**spaces**; yield, kilograms per vine and tonnes per hectare derive from
**planted vines**.

**Where they had been conflated, and what it changed:**

- One site's planting areas were derived from *planted* vines rather than
  spaces, which understated the area of the block with gaps by nearly
  7%. The other site's areas are surveyed and unaffected.
- The harvest screen's extent arithmetic pro-rates a planting's vine
  count across a picked row range. That is a grid question and should use
  spaces; it used the planted count. It understates the extent wherever
  there are gaps.
- The composition table counts planted vines, now documented as such — a
  vacant space belongs to no clone, which is why composition sums to
  planted rather than to spaces.

One block's sheet total turns out to be **neither** figure: its own
dead-or-missing and young columns sum to the grid, and the total it
states matches nothing. Recorded as superseded with the reason, not
deleted.

**Vacancy is an interval, not a flag**, so the count is correct as at any
date and a replanted or layered space closes its own vacancy. A boolean
would have made last season's count unrecoverable the moment a gap was
filled.

**"Vacant", not "dead".** A space that never had a vine is in exactly the
same state as one whose vine died, and nothing in a count can tell them
apart. The reason is recorded where known and is not required. Where a
source gives a number of gaps without saying which spaces, the count is
held against the planting rather than pinned to invented positions.

## 3. Data-quality register

A register that holds **both** figures and their sources where sources
disagree, picks no winner, and stays open until someone closes it with
what they found in the vineyard. Three entries so far, including the
block whose sheet spacing disagrees with its survey.

## 4. Training system

Now an attribute of the planting. Rows and bays are untouched: they are
how the vineyard is navigated on foot and do not change with how the
vines are tied.

## 5. Extent as coordinates

One resolver takes a block, a row range, a bay range, a drawn shape, or
any combination, and returns the same vine set — so the three ways of
describing an extent are genuinely interchangeable, and composition comes
out on the same basis whichever was used.

**Bay is its own axis and cannot be computed.** The obvious model — bay
as a function of vine position and vines-per-bay — is wrong for every
block checked. Bays do not start at 1 and do not increment with position;
they are the vineyard's own posts, numbered as the vineyard numbers them.
Which is exactly why they are useful to navigate by, and exactly why they
must be stored and queried rather than derived. Checking that before
building on it is the only reason it is known.

## 6. The press residual — what the evidence says

**The over-claim is in one barrel's line. No destination is missing.**

The barrel log's own totals row gives a figure for each of the two
fermenters involved, and the component columns of the six barrels
carrying either lot sum to *exactly* those figures. Every other barrel's
components equal its stated volume or fall below it; one barrel's
components exceed its stated volume, and that gap is the residual.

**A missing destination would break that reconciliation** — if a seventh
barrel had taken the volume, the components could not already sum to the
fermenter totals. So the earlier reconstruction stands.

The one alternative the evidence cannot exclude: that barrel's recorded
*capacity* could be wrong. The barrel log is the only statement of its
size on record. Worth a tape measure.

Everything stays categorised as unexplained either way.
