# 2026-09-27 12:40 — The map and its Layers panel with no signal

*Block layouts, vine counts, yields, input products and rates, client
names and certification details are withheld from this public copy.
This entry is about how the map behaves with no signal, and contains
none of them — the block it mentions holding offline is a test fixture
with a made-up outline — so nothing has been cut.*

The task queued at the end of the last entry: with no signal the map
could draw tiles held on the phone, but the Layers panel would not
open. Mike pasted it into this session.

## The task's premise was partly wrong — mine

The task (which I wrote an hour earlier) asked for verification by
reloading the page offline. That cannot work in this app, whatever the
panel does: `app/page.tsx` is a server component that asks the server
who is signed in before drawing anything, and there is no service
worker, so with no signal a reload never reaches any of this app's
code. Checked, not assumed — see below. It also said a map opened
offline shows "Your map layers could not be loaded"; in fact the whole
map is replaced before that line could ever show.

## Baseline: four ways a phone meets no signal (unchanged code)

Local Supabase, the test flight tiled by the app, Block A held on the
phone (15 tiles), headless Chromium with the connection cut:

1. **Map open, signal goes, Layers opened** → "Could not load the map
   layers … Failed to fetch". The map itself kept drawing (9 of 9).
2. **Signal goes, another tab, back to the Map** → the whole map
   replaced by "Could not load the map … Failed to fetch". No Layers
   button at all. (Tabs unmount; the map re-asks the server for blocks,
   sites and base maps every time it opens.)
3. **Reload with no signal** → the browser's own "No internet" page
   (`net::ERR_INTERNET_DISCONNECTED`). No app code runs.
4. **Signal goes before the Map was ever opened this session** → **the
   whole app down**: "This page couldn't load — Reload to try again".
   The map's code is a separate download (`next/dynamic`, since Leaflet
   needs a window) and "Loading chunk 761 failed" was not contained
   anywhere. Worse than the task described.

A server action called with no connection rejects with fetch()'s own
`TypeError: Failed to fetch` (Chrome) — which is what lets "could not
reach the server" be told apart from "the server answered with an
error".

## What changed

- **`app/lib/lastSeen.ts` (new, no relative imports, tested).** Keeps
  the last answer from the server per signed-in person
  (`vitifi.lastSeen.v1.<what>.<user id>` in localStorage, stamped with
  when), hands it back only if it is that person's and the right shape,
  forgets one person's copies on sign-out, and says when a copy is from
  ("1:15 pm today", "yesterday at 3:40 pm"). `couldNotReach()` is true
  only for fetch's no-connection errors (Chrome, Safari and Firefox
  wordings) or a browser that says it is offline.
- **`app/lib/mapCopies.ts` (new).** The map's three copies — layer list,
  storage totals, blocks/sites/base maps — with their names and shape
  checks in one place, so the map and the panel cannot drift apart.
- **Layers panel.** A successful load is kept. When the server cannot
  be reached it shows the kept list under a banner: "No connection to
  the server, so these are the layers as they were at …. Anything
  changed since is not shown", what still works, the raw reason, and
  **Check again**. **Any other failure is still a load failure** — a
  server that answers with an error is a fault to see, not to cover with
  an old list. Tiling polls stop while showing the kept list.
- **Map.** The same for its own base data: with no connection it opens
  from the kept copy and says so on the map. The layer list it loads on
  opening falls back the same way. A contour lookup that could not reach
  the server no longer takes the whole map down with it (contours need
  live LINZ tiles anyway, so the map opens without them; their button
  hides itself). Any other contour failure still does, as before.
- **Writes, decided:** with no connection, showing, hiding, fading and
  reordering change **this phone's map only and are not saved or
  queued**. They are shared settings (`map_overlays.visible` is one
  value for everyone), and the offline queue's safety comes from
  records being idempotent on a client ref, not from last-write-wins
  settings — a hide replayed hours later could quietly undo someone
  else's change made since. Tiling, "Download original" and holding more
  tiles need the server or storage, so they are hidden or disabled
  ("Needs a connection."). The held count and **Release** work (they
  only touch the phone's cache). Separately, a display change that
  failed *online* used to reject unhandled and leave the screen showing
  a change the server never saved; it is now said, and re-read.
- **Reorder shows on the map at once**, including offline: the map is
  handed layers in the panel's own order rather than the server's last.
- **The map's code is fetched in the background** once the app has
  settled (idle callback, or 3 s on Safari): about 70 KB compressed,
  less than two drone tiles. A failed fetch is ignored; the tab fetches
  it again when opened.
- **`ContainFailure` (new).** The Map and the drawing screen are wrapped
  in an error boundary, so a screen that fails while drawing fails on
  its own. A missing code chunk says "This phone has not downloaded this
  screen yet, and could not fetch it now. Reload once there is signal."
- **Signing out forgets that person's copies.**
- **The map's notes and its legend share one column** at bottom left.
  Both were pinned to that corner and the legend was drawn over every
  note (position accuracy, contours) — pre-existing, found because the
  new "no connection" note came out half hidden.

## After: the same situations, and four more

- **1** → the kept list under the banner; Tile it again and Original
  not offered; Hold disabled with "Needs a connection."; hiding the
  layer took it off the map with **0 server actions attempted**; shown
  again, 9 of 9 drawn.
- **2** → the map opened from the kept copy, with "No connection to the
  server: this is the map as it was at …"; the layer drawn (9 of 9);
  Layers opens, with the banner. Release with no signal gave back all
  15 held tiles.
- **Not saved means not saved:** hidden offline; the database still said
  `visible = true`; signal back, **Check again** → banner gone, layer
  shown again.
- **3** → still "No internet". Unchanged; see "Left undone".
- **4** → the app reopened on another tab: the map's code was fetched
  in the background (the main map chunk appeared in the request log);
  signal cut; the Map opened from the kept copy.
- **Map code blocked outright** → "Could not load the map … This phone
  has not downloaded this screen yet …" inside the Map tab; the Parcels
  tab still worked.
- **Shared phone:** signing out left 0 kept copies; the hand, who had
  never opened the map, got "Could not load the map" with no signal —
  nothing of the owner's shown.
- **Server answering 500** (every server action intercepted) → "Could
  not load the map layers … Internal Server Error", not the kept list.
- **Phone width, 375 px:** the note, the legend and the Layers button
  measured apart from each other (see below for what does still
  overlap).

## Where I was wrong

- The task's reload verification, as above: a premise I wrote without
  checking how the app's front door works.
- A test of mine expected "yesterday at 4:40 pm" for 03:40 UTC on 26
  September. It was standard time (+12) until early on the 27th, so
  3:40 pm is right; the test was fixed, not the code.
- My first edit moving the legend left it one closing tag short — the
  typechecker caught it before anything ran.

## Left undone, and open

- **Opening or reloading the app with no signal.** Needs an offline app
  shell (a service worker) and a way to know who is signed in without
  asking the server — a real decision on a shared phone, not a detail.
  It also matters more than it sounds: a phone that discards a
  background tab reloads it, and with no signal that is "No internet".
- **On a phone the Base layer box covers most of the map**, and any note
  at bottom left now sits over its last row; the legend overlaps the
  Layers button by 2 px. Pre-existing layout crowding at 375 px.
- The map's base data is only refreshed by reopening the Map tab once
  the signal is back; the panel's **Check again** refreshes the layer
  list only.
- The kept copies are as fresh as the last time the map or panel loaded
  with signal; nothing refreshes them in the background.
- Not tried on the live project or a real phone (no keys here; headless
  Chromium's "offline" is a clean cut, where a real phone at the edge of
  signal can hang instead of failing fast).
