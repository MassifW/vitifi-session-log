## A tiling job nobody is running no longer looks like one that is

**The fault.** Tiling runs in the browser of whoever added a layer. If
that tab closed, `map_overlays.tile_status` stayed `running` for ever and
every open Map panel re-read it every 4 seconds, all day. Worse than the
task described: each tick was **two** server actions (the layer list and
the storage totals), so one forgotten tab was ~14,400 calls a day, not
7,200 — on Netlify's free plan, the one realistic way to use up the
month and take the site down.

**Stalled is derived on read, no migration.** `map_overlays` already has
`updated_at`, bumped by a trigger on every update, and every progress
report is an update. `app/lib/tilingState.ts`: a pending or running job
silent for more than 10 minutes is stalled. Decided in `listLayers` on
the **server's** clock, so a phone with the wrong time cannot misjudge
it. (Progress is reported every 50 tiles — seconds apart even on a slow
uplink — so ten minutes is a wide margin.) A display change to a stuck
layer also bumps `updated_at` and delays the verdict by one period; said
here rather than engineered around.

**The panel** polls only while a job is genuinely going, re-reads only
the layer list (the totals refresh when a job ends), and backs off 4 s →
6 → 9 → 13.5 → 20 → 30 s. A stalled job says "Tiling stopped part-way,
at 37% — nothing has been heard from it since …, the phone or computer
doing it probably closed the page or lost signal", and polling stops. A
failed check now says so inline with **Check again**, instead of
replacing the whole panel and quietly stopping for good.

**Tile it again**, for a stalled job or a failed one that has a pixel
size (a file the browser never decoded would only fail the same way):
the confirmation states the original's size and warns off wifi, then
this device downloads the archived original and re-cuts the tiles.
Offered only to roles that can write vineyard data (`canWriteVineyard`,
the RLS mirror); others are told who can. Adding and re-tiling now run
one routine, `app/lib/tileLayer.ts`, lifted out of `AddLayerFlow`. The add
screen used to say "You can close this — tiling carries on"; true of the
box, false of the page, which is exactly how jobs were abandoned. It now
says to keep the page open.

**Also found: a second road to a stuck layer.** `reportTilingProgress`
and both writes in `finishTiling` discarded their database errors, and
`AddLayerFlow` ignored `startTiling`'s. A finish that failed to save left
the row `running` with nobody told. All now throw or are checked.
`replaceLayerPlacement` dropped a delete's result too (it has no caller
today; if one is added, the layer it leaves `pending` is now caught as
stalled and re-tiled to the new placement). **New guard** in
`tests/silent-failure.test.mjs`: no `await supabase.from/storage/rpc`
with its result thrown away. Run against the old file, it named all four.

### Proved in a browser, not just in tests

The app built against a local Supabase (migrations applied, the site
locations the migrations cannot recreate filled in by hand, a test owner,
a 2000×1500 PNG as an archived original, two `running` layers — one
silent for 30 minutes, one live), driven by headless Chromium:

- the stalled layer said so; the live one said "Tiling — 12%";
- **5 server actions in 62 s**, 3.9 / 6.1 / 9.1 / 13.6 / 20.4 s apart
  (the old code: ~31 ticks × 2);
- the live job made silent: called stalled at the next check, then
  **0 requests in 45 s**;
- **Tile it again**: size and mobile-data warning first, done in 10.5 s,
  279 tiles; then again over the existing tiles (the real case — a
  stalled job leaves some behind): done in 10.7 s, 279 tiles, no
  duplicates.

### Found by running it

- **The Layers button was covered** by the block-count label at every
  size measured (1280, 375 and 1920 px wide): both were pinned to the
  same corner and the label was drawn on top, so a tap on the icon did
  nothing. The browser test could not open the panel. The label now sits
  in the button column, below the buttons.
- **A finished layer is never drawn on the map** — pre-existing, and not
  fixed here. `useMapLayers.ts` signs `{minZoom}/0/0.png` to build a tile
  template: that tile is the world's top-left corner and never exists
  for a New Zealand layer (Storage: `404 Object not found`), the error is
  swallowed, and the layer is skipped — **0 tile requests** with the
  layer `done`, while the panel says "Shown at 10.2 cm". And even a real
  tile's signature cannot open another (`400 InvalidSignature`), so the
  template approach cannot work at all. "Hold on this phone" uses the
  same trick. Queued as its own task with the evidence and the method.

## A run that could not reach the database now says so

`npm test` without `.env.local` (every cloud session) used to end
"221 pass, skipped 0" with twelve live-database suites — about eighty
tests — never run. Node counts a skipped `describe` as a suite and its
tests as nothing; confirmed with a two-line probe before changing
anything.

- `tests/support/live.mjs`: `describeLive(name, fn)`. Offline, each
  suite is registered as **one skipped test**, named "… [live database]
  # SKIP NOT RUN - needs .env.local", so the summary reads `skipped 12`.
- `scripts/run-tests.mjs` (now `npm test`) runs exactly what ran before
  and ends with one line: "LIVE DATABASE: 12 suites NOT RUN - … row-level
  security, the ledger, the schema contract and the security surface went
  unchecked", or "all 12 suites that need it ran".
- **No opt-in required to skip — decided, and why:** cloud sessions carry
  no secrets by design, so failing by default would fail every cloud
  session, and a flag everybody sets by reflex is a skip nobody decided.
  The reverse exists instead: `VITIFI_REQUIRE_LIVE=1 npm test` makes a
  missing `.env.local` a failure, for a machine meant to have it.
- `tests/live-suites.test.mjs`: no bare `skip:` on a live suite, every
  file reading `.env.local` uses `describeLive`, and a probe run proves a
  skipped suite is *counted*. Putting the old behaviour back inside the
  helper turned the probe red.

Checked all three ways: offline — 245 pass, 12 skipped, the NOT RUN line,
exit 0; `VITIFI_REQUIRE_LIVE=1` — exit 1; and with a temporary
`.env.local` pointed at the local Supabase — all 12 suites ran (310
tests), the line said so, and 21 failed, every one about data only the
live database holds (vine positions, the imported vintages' volumes,
particular barrels). The temporary file was deleted straight after.
My own new line first said 13 while the summary said 12 — it was
counting `describeLive(` inside the guard test's strings; it now counts
top-level declarations only.
