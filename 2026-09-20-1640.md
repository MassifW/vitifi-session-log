# 2026-09-20 16:40 — A vessel measured, a racking path, and an area that was dividing by the wrong thing

*Volumes, yields, vine counts, block layouts, composition percentages
and input rates are withheld from this public copy. The findings, the
reasoning, the defects and the corrections are all here.*

Four pieces: apply a physical measurement that had been held as an open
question, build the path a cellar record will be entered through, fix
two findings from yesterday's audit, and write down what the app needs
from that record. Three defects turned up that nobody was looking for,
and one was worse than anything on the list.

## 1. The vessel was wrong, not the line

A concrete egg had been recorded at one capacity while the press sheet's
component columns said it received substantially more. Yesterday that
was logged as a data-quality item holding both figures and picking
neither, explicitly not pre-applied. It has now been measured, and the
components were right.

Applied as an append-only correction:

- the vessel's capacity updated, with the reason kept in the row rather
  than only in a commit message;
- the original movement **superseded, not edited** — a new dated
  adjustment carrying the log's own component volumes, with the
  superseded row untouched and still readable;
- the two loss rows a previous reconstruction had written are
  **retracted by superseding zero-litre rows**. The loss table required
  a strictly positive volume; zero is now permitted and documented as
  meaning only "this loss did not happen".
- a new `loss_current` view — the head of each chain with retracted
  heads dropped. Nothing had ever read the loss table: no view, no
  server action, no screen. The retraction would have counted twice
  without it.

**Independent corroboration, and it is strong.** With the corrected
capacity, the two fermenters that fed the vessel reconcile *exactly* to
the figures the barrel log carries in its own fermenter rows — to the
litre, on both. Before the correction they were short by the disputed
volume. That is a second source agreeing, and it has nothing to do with
the tape measure. It is now a test.

**Admitted in the migration.** The earlier press-split reconstruction
brought two movement lines down with an in-place `UPDATE`. That was
wrong in method — the originals are gone from the database and
recoverable only from the source log. It was also redundant: the view
behind the figures already pro-rates each line down to the destination's
volume, so rewriting the rows achieved nothing the view was not already
doing. This correction does not repeat it.

## 2. Racking

The record is held by the winemaker, so this builds the path and enters
nothing.

### The ledger was going to get a rack wrong

Found before building on it, by asking what a rack would do to the
balance views rather than assuming they would cope.

Every movement in the database so far brings wine into vessel tracking
for the first time — a press off a fermenter, a blend assembled from
fermenters. **No vessel is currently both a destination and a source.**
So the attribution view credits a movement's source lot, which is right
for a press (the fermenter's contents were never credited, so pressing
is the only record of that wine) and wrong twice over for a rack: the
wine was already counted when it went into the barrel, and the barrel it
left is not debited.

Racking a single barrel would have added roughly twice that barrel's
volume to the vintage. A day's racking would have added a vintage and a
half.

Fixed: recovery excludes racking outright, because it measures what the
press gave and moving wine afterwards does not change it; the in-vessel
view gains a branch that nets a rack to what arrived less what left.
Every existing figure is identical before and after, because with no
rack in the database the branch is unreachable.

### Two things called "loss", with opposite arithmetic

The loss rows already in the table are press residuals off fermenters:
that volume never reached a vessel and nothing ever credited it, so
subtracting it would take the same litres off twice. A racking loss is
the opposite — that wine was in a barrel, counted there, and is now
lees.

Same table, same categories, opposite arithmetic. So the table gains a
column saying which kind it is, set explicitly on the existing rows. It
could be inferred today, but only by accident of what has been imported,
not by anything the data means.

### Proving it without inventing a racking

A PL/pgSQL block with its own `EXCEPTION` clause is a subtransaction: it
writes a real rack against a real barrel, reads every figure it moves,
raises a user-defined SQLSTATE to undo all of it, and returns the
readings in variables, which survive the rollback. Nothing is left
behind — no movement, no loss, no scratch vessel — and the test asserts
that too. It also measures what the old arithmetic would have said, so
the regression is a number rather than a description.

### The screen

A maths module with no database and no React in it, a server action
layer, and a Rack view in the Cellar.

- **Sources added in a batch** from a checklist of what is holding wine.
  A day's racking is one pass through the screen, not one per barrel.
- **Destinations per source** — an existing empty vessel, a vessel the
  app does not have, or topping wine. One source into several
  destinations is the normal case.
- **A new vessel is created from the same form.** Sending a cellar hand
  to a settings screen mid-session is how a record stops being entered.
  Idempotent on site and code.
- **Volumes pre-filled** from the vessel's rated capacity, and only
  while the field is still the pre-filled one — typing a number makes it
  yours. Assumed figures are marked on screen and carry the assumed flag
  into the ledger. A whole vintage of nominal figures is exactly how the
  egg came to be recorded at the wrong size.
- **Lees** measured per vessel, or one session total split across the
  vessels by what each held with largest-remainder rounding so the parts
  add back to the measurement exactly, or derived from the ledger and
  labelled as derived. With none of the three, **no loss is claimed at
  all** — zero would be a statement that nothing was lost, and nobody
  made that statement.
- **Topping wine** takes the vessel-less shape already built for the
  earlier vintage's topping blend, with parentage written so its
  provenance works.
- **Warns, never blocks.** More out than in, a loss over a threshold, a
  destination over its own capacity, a measured loss that disagrees with
  the ledger — all warn and save.
- **Idempotent per source**, not per session: a signal drop halfway
  through a day's racking must not re-enter the ones that landed.

One source emptying is one event, and the movements it caused carry its
id. No new table — events is already the record of what a person did.

### Where the model and the brief disagree, stated rather than smoothed

The brief describes a source emptying into several destinations as one
movement with several lines. The ledger is the other way round: a
movement has one destination and its lines are its sources, chosen
deliberately so a barrel's composition is read rather than prorated. A
fan-out into three vessels is therefore three movements. The **event**
is the unit the brief describes and it is one row; the movements hang
off it. Same idea, opposite orientation, and worth knowing before
reading the ledger.

### The gap, flagged and not filled

A data-quality item for the vintage rather than one per vessel: the
ledger is right about what was pressed and wrong about where it is, and
it carries a racking loss of exactly zero. A real cellar a year on does
not have a gap of zero. Nothing is reconstructed, and a short document
now says what the app needs from the record.

## 3. Area is a question about ground, not about vines

Two findings from yesterday's audit, fixed together.

**The first.** Effective area divided the picked *vines* by vines per
hectare. Vines per hectare is a spacing calculation — a statement about
the grid — so the thing divided by it has to count the grid too. Using
planted vines leaves out the ground under every vine that died and
overstates tonnes per hectare by the vacancy rate of whatever was
picked. Negligible at one site; several percent at the other, where the
vacancy is real.

**The second.** The vine count for a picked range was pro-rated: the
planting's total scaled by the fraction of its rows the range covered.
Rows are not uniform. One range pro-rates to roughly two-thirds of what
it actually holds. The per-row counts have been in the database since
the vine import and nothing had read them.

Both fixed by counting. A new function answers, for any extent by
block, rows, bays or drawn shape, how many vines grow in it and how many
spaces it covers. A companion view gives the entry screen every
planting's rows in one query, so a phone at the weighbridge sums
whatever range is typed rather than calling the database on each
keystroke.

**No stored figure changes**, because no pick line exists yet and no
historical pick resolves to an extent. This is prospective, and the size
of it is recorded per planting in the private entry.

**The acceptance sheet is unchanged, which is the point.** The rows that
sheet picked carry no vacancies, so its effective area and its tonnes
per hectare come out exactly as before. The correction moves one site
and leaves the other alone. That is asserted in a test, not assumed.

**What the counted path surfaces.** The crew's own vine count and the
vine census disagree about the same rows, and so do the composition
sheet and the census for another planting. **Both are kept in each
case.** The count wins for kg per vine, because it measures what was
picked and the census was taken on another day; the disagreement is
shown on the line rather than resolved by arithmetic.

A line that names no rows now resolves to **nothing** rather than to the
whole planting. Handing a small add-on load the whole block's vines
produces a kg-per-vine and a tonnes-per-hectare that look like figures
and are not.

## 4. Three defects found on the way, none of them on the list

### A screen giving a false all-clear

The worst thing found today. The reconciliation panel selected a column
that **stopped existing two days ago**, when the view behind it was
rewritten to carry two figures in place of one. The database rejected
the query. The panel's `Promise.all` had a `.finally` and **no
`.catch`**, so it rejected, neither figure was set, loading went false,
and the screen settled into its empty state announcing that there was
nothing to reconcile and every lot traced back to its fruit — with
**five lots flagged**. It had been lying for two days and nothing caught
it, because its failure mode is indistinguishable from success.

Fixed at both ends: the query asks for the columns that exist, and the
panel now has an explicit failure state saying *nothing below is a
statement about the ledger*. It also shows both vintage figures now
instead of one, which was the point of splitting them in the first
place.

### The same screen reporting corrections as open anomalies

The gap check read the whole movement table, superseded rows included,
so it was showing three discrepancies that a migration had superseded
the day before. A correction that does not stop the complaint is not a
correction. It now reads the head of each chain, and there are no gaps
left.

### A 500 on page load, and the log said exactly what was wrong

A `'use server'` file exported a constant array. The framework allows
only async exports from those files, the console said so in those words,
and the server log named the file. One edit, confirmed by a fresh tab
with a clean console and a server log of nothing but 200s.

Worth recording because it is the counter-example to the debugging note
added to the project's instructions yesterday: the log said what was
wrong, and reading it was the whole diagnosis. The failure last time was
not reading it.

## 5. Two more data-quality items raised, neither fixed

- **Two barrel codes that read as dates** — almost certainly what a
  date-formatted spreadsheet cell does to a code with a slash in it.
  Almost certainly is not a record, and renaming a vessel on a guess
  puts a barrel in the ledger that nobody can find in the cellar.
- **A barrel with no code at all.** Found by driving the racking screen:
  it rendered as a blank line in the destination list — invisible and
  selectable at once. The screen now labels it. It holds nothing, which
  is exactly why it is worth fixing now.

**And one item I created and had to clean up.** The migration raising
the first of those was re-applied after an edit, which inserted the row
twice. The duplicate is marked superseded with the reason rather than
deleted, and the insert is now guarded so it cannot recur.
