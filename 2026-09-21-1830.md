# 2026-09-21 18:30 — Map layers: one button and a file

*Volumes, yields, vine counts, block layouts, composition percentages
and input rates are withheld from this public copy. The findings, the
reasoning and the corrections are all here.*

Seven things asked for. All seven built; one of them — reprojection —
is deliberately incomplete and says so rather than guessing.

## The elevation question, first, because it decided everything else

**Does LINZ LiDAR elevation cover both vineyard sites?** Yes. Checked
by decoding real tiles rather than reading a coverage map: plausible
heights at both, with a real local range across each tile, served all
the way to zoom 20.

The route is **LINZ Basemaps' terrain-RGB elevation tiles**, not the
Data Service. That matters: the Data Service key still returns 403 on
its query API — the message has changed but it is the same missing
scope — while the Basemaps key works and needs no layer-id lookup. Two
different services, two different keys, and the one that works is the
one the app was not using.

At zoom 17 a pixel is about 0.85 m, which is roughly the native
resolution of the LiDAR underneath. So a 1 m contour interval is sound
and is the default; 0.5 m is the floor, and a finer request is clamped
with the screen saying why; below that it would be drawing
interpolation and calling it ground.

**Contours are generated in the browser, not stored.** Storing them
would fix the interval once, keep a copy of public data, and go stale
the next time LINZ reflies. The zoom is chosen by the interval, so a
1 m interval fetches about thirty tiles rather than the three hundred
the next zoom down would cost for detail the source does not have.

## Adding a layer, and placing it

Detection reads **bytes first, name second**. A drone pipeline that
writes a GeoTIFF and calls it `.tif`, a phone that renames a PNG, a
browser reporting a generic content type — all normal.

GeoTIFF georeferencing is read from the file's tags **without decoding
a single pixel**, because placement does not need them and a drone
orthomosaic is hundreds of megabytes. KML and KMZ give up their ground
overlay and their placemarks; a four-arbitrary-corner overlay is
**refused rather than squashed into a box**, because squashing it moves
the image. GeoJSON goes straight on. A zipped shapefile gives its
geometry and its projection code. A photograph or a scanned plan opens
placement mode.

**Placement mode shows the image and the map at once** — the
instruction is "tap a feature on the image, then the same spot on the
map", which cannot be done if one is behind the other.

Three findings the tests forced out of the fitting maths, each of which
changed the design:

1. **With exactly three points the error is zero by construction.** The
   fit passes through every point. Showing a reassuring zero would be
   reassurance the arithmetic invented, so the screen says the error
   cannot be measured yet and asks for a fourth point.
2. **A "worst point" is only named when one genuinely stands out.**
   Several points disagreeing equally is the normal shape of an
   imprecise placement, and naming whichever of them floating-point
   arithmetic put a hair above the rest would send someone to move a
   perfectly good pin.
3. **Three points in a line are refused.** Three fence posts along a
   row is exactly how a careful person produces three useless points,
   and without the check the fit blows up and the image lands in the
   ocean.

The preview draws through the full transform, so a **rotated**
placement previews as rotated — the map library's own image overlay is
axis-aligned only, and previewing a rotated placement as square would
show the user something other than what they are about to save.

Corner-dragging is offered as the quick alternative and says in words
that it cannot express rotation.

## The record, and the panel

The existing overlay table was widened rather than a second one
started. It gains type, capture date (which one column already was, now
documented as the day it was flown rather than the day it was
uploaded), season, visibility, opacity, order, the transform, the fit
error and its point count, the source format, and a tiling state
machine. Match points are their own table — the transform is derived
and the pins are the evidence, so re-opening a placement in a year
shows the points to move rather than six numbers to edit.

The panel groups by type, newest capture first. Each layer gets its own
map pane, which is what makes reordering, per-layer opacity and the
swipe comparison work at the same time. The swipe is a clip on two
panes — no plugin, no second map, and the two layers stay exactly where
they are, which is the point when the question is whether something
moved between them.

**Every hand-placed layer says so, every time, with its fit error.** A
pinned layer and a georeferenced one look identical on screen and are
not the same kind of evidence.

## Large files, and what keeping them costs

Tiling runs in the browser, because the file is already there. The
screen is released as soon as the layer is on the map; tiling carries
on and reports into the panel. A layer whose tiling failed **still
shows** — whole and slowly — and says why, because that is a quality
note rather than a broken state. The cost is worked out before the
upload starts, so the screen can name the number of tiles rather than
discovering it.

The honest limit: a browser canvas caps out around 120 megapixels on a
typical device, and the finest-resolution flight over the larger site
would be about 177. That case is stored whole and says so. Doing better
needs GDAL on a server and is not pretended at.

**Ten seasons of three flights a year comes to under 6 GB** — a few
percent of what the current hosting plan already includes. Storage is
not the constraint and there is no reason to delete an old flight.
Transfer is the figure to watch instead: an untiled orthomosaic is the
whole original every time someone opens it, against a couple of
megabytes tiled. That is a better argument for tiling than speed.

## In the field

Live GPS with **its accuracy circle**, which is not decoration: a phone
in a vineyard is routinely five to fifteen metres out, and a dot
without a circle invites trusting it to the metre. Permission is
requested only when the button is pressed — a map that demands location
on open trains people to refuse. Dragging turns following off, because
a drag means the person wants to look somewhere else.

## Found on the way

**Storage had no policies at all**, and it had not mattered while
everything went through the privileged key. Since the switch to the
caller's own client it meant every upload and every signed URL would
fail, for everyone. Both buckets were empty, so nothing was actually
broken — luck of timing. Policies added for all three buckets, all
private, no delete policy, and the security sweep now reports buckets
so a public one cannot appear unnoticed.

**A server-actions file exported a constant map for the third time in
two days.** The production build did not catch it. The test written
after the second time did.

**My own security report cried wolf** — it compared a Postgres option
to the wrong literal, so its first run flagged every correctly
configured view, which would have buried the two real findings
underneath.

## What is deliberately not built

**Reprojection.** A georeferenced raster in the national grid rather
than latitude and longitude is the normal output of a local drone
pipeline. This reads its projection code but does not convert it:
rather than place the file wrongly, it goes through placement mode,
which still produces a measured fit error. PostGIS is installed and has
the whole projection database; doing it there is the next piece, and a
hand-rolled approximation would have been wrong in a way nobody noticed
for a season.

Also not built: applying a declared rotation from a ground overlay (it
is placed without it and says so), and server-side tiling for rasters
past what a browser will slice.
