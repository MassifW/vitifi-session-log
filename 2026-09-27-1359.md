# 2026-09-27 13:59 — VITIFI opens with no signal

*Block layouts, vine counts, yields, input products and rates, client
names and certification details are withheld from this public copy.
This entry is about opening the app with no signal and who sends entries
held on a phone, and contains none of them, so nothing has been cut.*

The task: VITIFI could not be opened, or reloaded, with no signal. Present
the options with their trade-offs before writing code; then build what
Mike chose, check it in a browser against a local database, and keep the
Harvest and Rack queues working from a phone that opened with none.

## Measured before changing anything

The last commit (99313af), built and served locally, a phone-sized
Chromium, the owner signed in on Harvest. Then a real outage — the
browser offline **and** the server stopped — and a reload:
`net::ERR_INTERNET_DISCONNECTED`, and the phone's own page: "No internet.
Try: Checking the network cables…". There was no service worker at all.

## Mike's three decisions

Put to him with their trade-offs; recorded in full in
`docs/decisions.md`, "Opening with no signal":

1. Build it, **with Serwist** (recommended).
2. **No time limit** on showing the last signed-in person's app with no
   signal — chosen over the recommended 14 hours, knowing a phone left
   in the ute for days still opens as them.
3. **Entries held on a phone are sent only by whoever made them**
   (recommended), because the database stamps whoever sends a row.

## What was built

- **The service worker** (`app/sw.ts`, rules in `app/lib/appShell.ts`),
  built by Serwist 9.5.12 into `public/sw.js` (generated, git-ignored).
  It keeps two things: every file of the app's code (51, precached),
  and the app page as the server last drew it for the person signed in.
  The page is kept only when it carries `data-vitifi-shell="signed-in"`
  and a staff id; dropped when the server draws the signed-out page;
  never kept or answered from the phone for a sign-in or reset link.
  Every load asks the server first and waits 10 s before using the copy.
  Each kept page is stamped with the app version that drew it; a new
  version redraws it on taking over, and drops an older one it cannot
  redraw. Serwist's ready-made caching rules are not used — they would
  keep Supabase answers fetched with one login and hand them to the next
  person. The worker gets a Content-Security-Policy allowing this site
  only.
- **The strip across the top** (`OfflineShellNote.tsx`) when the page is
  the phone's copy: "No connection to the server. This is VITIFI as it
  was when <name> last opened it with signal, at <time>." The worker
  says which windows it opened from the copy, since a copy kept seconds
  ago looks like a fresh page.
- **Held for their maker** (`app/lib/offlineQueue.ts`): each held entry
  records who made it; sending sends only the signed-in person's; the
  others are listed as "entered by <name>" and wait. Entries held before
  today carry no maker and anyone may send them, as before. Racking
  sends on its own when the signal returns — that path now sends only
  the maker's too.
- **Harvest and Rack open with no signal** (`app/lib/fieldCopies.ts`):
  each keeps, per person, the lists its form is built from (sites,
  plantings, lots and tares; vessels and what each held) and its recent
  list, used only when the server cannot be reached, and labelled with
  the time. The Cellar tab, when it cannot load, still offers Rack to
  those who may rack. With no lists at all, "New pick" and "Add vessels"
  are not offered, and the screen says why.
- **Signing out with no signal** (`app/lib/signOutHere.ts`): it asked
  the server and, with no signal, failed silently, leaving a shared
  phone signed in. Now the phone deletes the login's cookies itself and
  reloads to the "needs a connection" page.
- **Honest messages.** Both screens held an entry on any failure and
  said "No connection — will send when there is signal", even when the
  server had refused it. They now say which. Racking no longer re-holds
  a session that saved, when the list reload straight after fails.
- Drawing a picked area says plainly that it needs signal.
- **Home Screen**: `app/manifest.ts`, icons (the header's grape, white on
  the app purple, source in `docs/icons/`), `appleWebApp` metadata.
- **Netlify**: skew protection on (`NETLIFY_NEXT_SKEW_PROTECTION`, read at
  build time by the adapter — checked in its source; free on every plan
  per Netlify's docs) and `/sw.js` headers repeated in `netlify.toml`,
  since files in `public/` are served from the CDN.
- The session middleware now skips `/sw.js` and the manifest.
- `npm audit`: Serwist pins browserslist 4.28.6 (2 high advisories);
  overridden to 4.29.1 in `package.json`, audit back to 0.

## Found that does not fit

**The Harvest screen cannot save a pick at all.** `createHarvestPick`
writes the `events` row with neither `target_area_id` nor
`target_lot_id`, and `events_check` requires exactly one. Reproduced on
99313af **with signal**: the database refuses (23514) and the old screen
said "No connection — saved on this phone and will send when there is
signal". Nothing had ever been entered through the screen in the local
database (all 24 picks there are imports, each pointing at a lot); the
live database was not checked. It needs a decision on what a pick event
points at, so it is a separate suggested task, not fixed here. The
screen now says the server refused it.

To check whose name a sent pick lands under anyway, the test run lifted
`events_check` **in the local test database only**, then deleted its
test picks and put the constraint back exactly (checked:
`pg_get_constraintdef` matches). For the racking half, the hand was made
a cellar hand for the run and set back to vineyard. The rackings those
runs sent stay in the local ledger, which is append-only.

## Where I was wrong, or the tools were

- My first "signed out, no signal" check only switched the browser
  offline. Playwright's offline switch does not reach a service worker's
  own requests, so the worker reached the running server and correctly
  got the sign-in page. Not the case I meant to test; the check now
  stops the server too, as every other no-signal check does.
- A run that crashed left a server on the test port serving a build that
  had since been deleted; the next run's sign-in "timed out". The test
  harness now refuses an occupied port.
- My first release check looked for `?dpl=` on the page's first script
  tags. Next puts it on the chunks loaded later, named in the page's
  data. The check was wrong, not the app; the stored page was byte for
  byte what the server draws.
- The same run's map "failure" was my test never opening the map with
  signal; the map's own "Could not load the map" proved its code had
  loaded offline.
- Once more, a `pkill` matched its own command line (exit 144).
