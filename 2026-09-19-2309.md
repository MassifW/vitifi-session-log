# 2026-09-19 23:09 — Topping wine, precision, and a correction to last session's claim

*Volumes, yields, vine counts, composition percentages and input rates
are withheld from this public copy. The findings, the reasoning and the
corrections are all here.*

## 1. Topping wine modelled

A topping blend is a lot that need never have a vessel. That is now
expressible.

- **The topping blend** — a `blend` movement with no destination
  assembles it from seven lots; a `top` movement consumes it a few
  months later. It carries parentage to its seven parents, so the
  consumption charges back to the fruit that made it.
- **A press blend whose barrel is not named** — a `barrel_down` with no
  destination. Not the same case: its barrel exists, the log just does
  not say which, and the movement says so rather than being waved
  through. It is still listed in the current round, so it is still held.

The destination constraint was replaced: a movement may have no vessel
when its type leaves vessel tracking (`bottling`, `transfer_out`, `top`)
or when its notes explain why there is none.

**The earlier vintage now ties to both of its log's own figures rather
than neither** — the barrelled-down total and the still-in-barrel total,
with the difference showing as consumed. Those two numbers sit in the
log's oldest and newest rounds and were never in conflict; the app had
simply been modelling only one of them.

Recovery now divides by what was **barrelled down**, not by what is left.
Dividing by what is left makes a vintage look worse the longer it sits,
which is a measure of ullage wearing the name of recovery. The balance
view reports both figures and the gap between them.

## 2. Clone and rootstock are estimates, and now say so

Every dimension carries a precision — `exact` or `estimated` — and
estimated ones carry the basis in full:

> Apportioned from the planting's vine counts: the picked rows cover more
> than one clone, and this assumes the pick took them in the proportion
> they are planted. A pick that worked one end of a block did not. Exact
> figures need the rows or the individual vines picked to be recorded.

Precision is shown on every dimension, not only the poor ones — a figure
that reads as fact when it was apportioned is the failure this guards
against.

**Exact is currently reachable for exactly one block**: the one planted
entirely to a single clone. Every other area a pick names covers a
planting with a clone mix, so any figure from it is apportioned. No pick
anywhere records individual vines.

### The same blend's clone breakdown, three ways

**Way 1** — the barrel log's own clone columns, volume-weighted across
the blend's barrels.

**Way 2** — derived: the log's own block percentages multiplied by each
block's planting clone mix. That vintage's picks carry no area at all, so
the planting chain cannot run from the picks; going via the log's block
columns is the only derivation available for it.

**Way 3 — what exact would need**: the picked rows, or the picked vines,
recorded against each pick. One block is the whole problem — it is the
only one with two major clones, and they sit in different row ranges. A
pick of the lower rows is entirely one clone; a pick of the upper rows is
entirely the other. With the rows recorded, that block resolves exactly
and the estimate disappears. Nothing else is needed: the plantings
already carry the clone and the vine count.

### Reconciling the two headline figures

The two numbers I was asked to reconcile are **from different vintages**
and should not reconcile — one is this vintage's blend from its own log,
the other is the following vintage's blend, which I quoted last session.
Different blend, different fruit, different year.

The real discrepancy is *within* one vintage: the log's figure for the
majority clone against the derived one, with the gap almost exactly
offset by the other major clone moving the other way. Both differences
come from one block and nowhere else.

Working backwards from the log's numbers shows it treats that block as
roughly one-third / two-thirds between its two clones. The vine census
says close to the reverse.

**The log is probably right and my derivation probably wrong**, because
the log knows something the pick records have lost. The winemaker picks
that block's two clones as *separate lots* — the lot names say so
outright. The log's clone column reflects which sub-range each lot
actually came from. The derivation cannot, because those picks carry no
area, and the following vintage's picks from the same block point at an
area with no row range either.

So the estimate spreads the block across its whole vine population when
the real picks were deliberately not spread that way. Which is exactly
why these figures are now labelled estimated.

### Correcting last session

I wrote that the derivation "is the better of the two" and that the log
"maps one clone per block and is wrong here". That was too strong, and
wrong for the one block where it matters. The log is not mapping one
clone per block — it is recording which sub-range each lot came from,
which is finer than anything the pick records preserve. Where the
derivation genuinely does add something is the interplanted rootstocks
that the log's fixed set of columns has nowhere to put.

## 3. The missing-block bug — what it actually touched

Introduced when the composition layer was first written; fixed one
session later.

**Stored: nothing.** The composition function performs no writes, no
migration or script derives from it, and the SQL views behind every
balance and reconciliation figure never referenced provenance or block at
all. Everything produced during the window was unaffected.

**Exported: nothing.** The export path has no reference to it.

**Shown: yes.** The only consumer was the blend detail screen's
composition sections. **12 of 50 lots** have picks spanning more than one
block, and for each the screen showed a single block at 100% instead of
the real split. Site and vintage were structurally affected by the same
overwrite but unaffected in practice — no lot spans more than one site or
more than one year.

The app is not deployed, so the only person who saw it was me, during
browser verification; the figures appear in two screenshots in this
session's messages. They were never stated as correct in prose, and in
the second instance I flagged the discrepancy and fixed it in the same
message.

Worth noting: the corrected splits match the barrel log's own per-lot
block columns exactly, for all twelve — independent confirmation that the
fix is right.

## 4. This log now withholds input rates of all kinds

The fourth exclusion was "spray products and rates". It is now "input
products and application rates of any kind" — sprays, cover crop
seeding, seed dressings, soil amendments, fertiliser. Naming the product
and describing the operation stays fine; the rate does not. Describing
the *shape* of a rate calculation discloses no quantity and stays fine
too.

The 14 September entry was the only one carrying rates and has been
amended to drop them while keeping the operation, the species and the
vendor product name.

**Caveat, stated plainly**: amending a file does not remove the earlier
revision from a public repository's git history. The old text remains
reachable to anyone who looks. Removing it entirely would take a history
rewrite and a force push — not done, because that is a destructive
operation on a published repository and wants an explicit decision.
