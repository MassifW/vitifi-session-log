## Topping

Cellar → "Top". A round is one event and one movement out of the topping
wine for the litres used. Barrels stay full in the ledger, as in the
barrel log, so the topping wine used is the ullage; the import already
treated a 2024 topping blend that way.

- **The list carries forward.** A new round starts as the last round's
  list from the same topping wine, every barrel ticked; unticking records
  a barrel as not topped this time. A first list can take a whole vintage
  at a vineyard in one tap.
- **The database works out the litres topped** from what the records hold
  in the listed barrels. A barrel the records think empty counts at its
  size, and the round says it assumed so. The screen shows % ullage per
  round, litres left after it, and the ullage over a year (the topping
  log's own sum: used ÷ average topped × 365 ÷ days).
- **Corrections and removals are new rows.** A removal is a retraction
  event plus a 0 L movement superseding the original. The movement ledger
  now allows 0 L only on a superseding row, as the loss ledger already
  did. Works offline. A topping file in "All records".
- 18 rolled-back checks run as a cellar hand, vineyard hand and reader,
  through row-level security, on live.

Walked through in a browser on a local copy of live: record, a second
round, correct, remove. The figures were checked by hand (two rounds 14
days apart: 19.16% a year). Every version stays in the ledger, and the
cellar's own volume check moved by exactly the litres used.

### Found on the way, and fixed before live

1. **A press blend was offered as topping wine.** The first rule took
   every lot with no vessel as topping wine, but some just have a barrel
   the log does not name. Now it is a lot named as topping wine (which is
   how pressing and racking name it) or one a round has drawn from.
2. **The real topping wines were buried** among about 100 barrels, because
   they sit in a keg. They now come first.
3. **Irrigation's records would have been in two export files.** The
   previous day's migration added a file for them but left them in the
   catch-all file too. The completeness check never read the new file, so
   its "no record in two files" could not see it. My mistake. Live had no
   irrigation records yet, so no export carried one twice. Fixed, and a
   test now fails on any events file the check does not read.
4. **The draft migration made a core ledger view run as its owner.** In
   Postgres, `CREATE OR REPLACE VIEW` replaces the view's options too.
   Without `WITH (security_invoker = on)` the view reads past every
   row-level security policy. It was caught on the local copy before the
   push. The live security test would have caught it, but only after the
   view was already open on live. Fixed, plus a new offline test that
   fails on any view a migration writes without the option.
