# 2026-09-29 10:03 — Every record readable outside the app; recommendations hidden; correcting floor work; a view that did not survive its backup

*Block layouts, vine counts, yields, input products and rates, client
names and certification details are withheld from this public copy.
Here that means record counts that describe the vineyards, and lot and
site names. The private copy has them.*

Mike said yes to a readable export of every record and to a watchdog for
the nightly backup, asked for the placeholder spray recommendations to be
hidden until they are real, and — after adding floor work — pointed out
that an entry could not be edited once made. Applied to the live
database on his word; not yet released.

## Found

- **The Spray Diary showed placeholders as facts**: a risk rating, an
  alert count and a "current stage" all came from a recommendation engine
  run on a fixed growth stage, no blocks and no spray history; two spray
  counts read zero whatever the diary held; and the engine could propose
  urgent tank mixes from its own built-in list.
- **Growth-stage readings cannot be entered in the app at all** — the
  existing ones are imports. So the honest pointer for real
  recommendations is "these need growth-stage readings, which can't be
  entered yet", not an entry that would change nothing. With budburst
  under way, a growth-stage entry is now the top suggestion.
- **Floor work had no way to correct a record**; nor do most other screens.
- One export column read the wrong field name; caught while reading the
  code for the correction work, before it went live.
- **The "missing" nightly backup was late, not missing.** GitHub started
  the scheduled night over six hours late (the night before, four). Earlier
  today it was written down as never having started; corrected.
- **And that late night's readable copy failed — my ordering.** It began
  eight minutes after the new code was pushed and before the database
  change it needed was applied. The backup itself was made and verified;
  the readable copy failed on its own and opened its own GitHub issue,
  which is the design working. The rule going forward: apply the database
  change before pushing code the nightly job runs.
- **One new view did not survive its own backup.** A backup run by hand
  after the change wrote the readable copy but failed the restore check:
  every row came back, but one export view's definition read back
  differently. Restoring that backup on the laptop showed why: the second
  half of a `union` had unnamed columns (a `null`, a text literal).
  Postgres prints no name for those; pg_dump writes them with explicit
  casts, and read back they are named after the cast's type (`int4`,
  `text`) and printed that way. Same view, same rows, different text. The
  laptop's checks had missed it because they applied the change on top of
  a restored copy, so no dump containing the new views had been read back.

## Built

- **"All records"**: every record in VITIFI as spreadsheet files — one per
  kind of record, with plain column names, the names of things rather than
  internal ids, and a README. Each file is defined once in the database and
  turned into CSV by one function; the app's download and a **nightly copy
  kept beside the backup on GitHub** use the same list and the same
  function, so the records can be read even when the app cannot. Values a
  spreadsheet would misread (rootstock codes, clone numbers) open as the
  text they are. Every recorded event lands in exactly one file — a final
  catch-all takes any kind not otherwise named — and a check proves it;
  the test suite fails if a database table is in no file and not excluded
  with a stated reason.
- **The watchdog**: the nightly job now reports to an outside service
  after every night, which emails if a good night hasn't been heard of for
  too long — the only way to notice a night that never starts. It waits
  for Mike to create the free account.
- **Recommendations hidden, honestly**: the tab says they aren't working
  yet and what they will need, and keeps the real five-day weather; the
  fake cards and counts are gone.
- **Views that survive a restore**: the view now names every column in
  both halves, and a new check does to every view what a restore does —
  reads its definition as pg_dump does, builds a temporary copy from that
  text and compares the two, then rolls the copy back. It runs in the test
  suite, and the change that added it refuses to apply if any view would
  fail. Loosening the nightly comparison instead was rejected: it is the
  one check that proves a backup is the database, and it cannot know
  which differences are harmless.
- **Correcting floor work**: "Correct" opens the record filled in and saves
  a new version with what was wrong; "Remove this record (entered by
  mistake)" does the same for a mistaken entry. Every version stays
  readable — nothing is edited in place — and an attached tractor track
  moves to the new version.

## Verified

On a fresh restore of the live database: the completeness check; every
file built and read back by an independent CSV reader, every row as wide
as its header; the nightly script; corrections and removal in a browser,
including a track carried across; the full suite. Then on live: applied,
the completeness check passes there, every file builds from live, and
the full suite passes against live. A backup run by hand then found the
view problem above. The fix: shown on the restored backup to catch the
old definition and pass the new, with the exported file byte-for-byte
unchanged; applied to live with Mike's yes; the full suite against live
passes; and a second backup run by hand passed all three checks, kept
both the verified backup and the readable copy, and closed its GitHub
issue itself.

## Where I was wrong

The mis-named export column; a test run that pointed at live before the
change was there (its failures were the checks doing their job); "the
scheduled backup never started" (it was six hours late); pushing the
nightly job's new step before its database change was applied; and
calling the export verified locally when no backup containing it had
been restored — one backup was marked unverified before the fix.
