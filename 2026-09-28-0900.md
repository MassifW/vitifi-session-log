## Irrigation: what the sources hold (not built yet)

- **Zones are in the vine maps**, as a tag on each vine naming its
  irrigation line or solenoid, and they cut across blocks. Neither site
  had ever had them imported: the database holds each vine's position
  only. The maps' living positions join to it exactly.
- **Tags that look wrong were checked against the vines either side.**
  At one site about 170 cells are Excel auto-fill (a dragged
  cell counts its trailing number up or down), all sitting in rows
  dominated by the real tag. At the other, three adjacent misspellings
  sit in a row whose neighbours split between two zones, so the map
  cannot settle them. Two blocks carry no zone tag at all.
- **Emitters.** One summary sheet's flow formulas give the emitter flow
  and spacing of an old inline dripline; newer blocks carry a per-vine
  dripper rate as a tag. The second site records none. The model's
  parameter sheet turned out to describe a different property's blocks.
- **Hand watering** is flagged on individual vines; the summary sheet
  for it misses one block's flags.
- **The water-balance model** (the owner's own, built years ago for
  another property) is a daily bucket with two home-made terms: a
  multiplicative daily retention and a heat adjustment to reference ET
  (Tmax to the power π). The technical spec describes the standard
  balance with crop coefficients by growth stage.
- **Reuse, and a gap.** The weather cascade (rain, ET0) and growth-stage
  resolution exist, but weather ingestion only runs when someone opens
  the Spray Diary, reaches back three days, and last ran on 16 Sep.
- **Mike's answers change the model.** No block is wholly dry-farmed;
  watering is by per-vine drippers (young vines, and old vines with
  water needs); the inline dripline is old, retained and rarely used.
  So dry farming becomes a per-vine fact summarised per block. Still
  open: valves for the untagged blocks, the typo mappings, and which old
  vines have drippers. Recording was not started.

## Tractor tracks (released)

**Asked for:** GPS tracking of the tractor, "as we would for spraying
or seeding". **What existed:** the map's live position dot and a free-
text "pattern" on the floor-work record; nothing recorded a route.

**Told Mike first:** it could not be ready before he started; capture
the job with a free logger app and attach the file later. He finished
the job before replying, so this first job has no track.

**The finding that shaped it:** the rows are closer together than a
phone's GPS error, so no single position can name the alley it was in.

**Built:**
- A GPX reader that refuses a file without times and says what it
  dropped; a writer for tracks recorded in the app.
- Row matching: straight runs along the rows are passes, judged over the
  last 5 m so one jumpy fix cannot split one. All passes are fitted to
  the alley grid together — GPS error drifts slowly, so passes are
  accurate relative to each other — which removes any fraction of a
  row. A whole-row shift cannot be seen in the track, so the alley the
  first pass started in pins it, and without it the screen says "placed
  by GPS alone". A pass beyond the outermost row is reported as outside
  the block.
- A `tracks` table keeping the logger's file byte for byte with its
  SHA-256 (append-only; a correction supersedes), and `track_links`, so
  one pass can be evidence for several records (the mulching and the
  seeding it pressed in) and be attached after the job is written up.
  Row-level security in the ask-once form. The site's rows come back one
  row per vine row, so the API's 1,000-row cap cannot cut them short.
- On the floor-work screen: attach a file (preview, drawing, starting
  alley, attach to the same day's other records) or record in the app
  (screen kept awake, every position kept on the phone, gaps named, a
  save with no signal kept until there is one). An iPhone gives a web
  app positions only while the screen is on and the page in front, so
  the screen recommends a logger app for long jobs.

**Verified:** unit tests on a synthetic block (jitter, a fraction of a
row of shared error corrected, a whole-row shift detected and pinned,
half-driven alleys, GPX edge cases). On a restored copy of live, a
synthetic track built from the real vine positions with under a metre
of shared error came out **one alley off alone, and exact when
pinned** — the reason the starting alley is asked for. The whole flow
in a browser against that copy, as a local-only test login; the stored
file and its checksum checked in the database. Applied to live with
Mike's yes; every test passes against live, typecheck and build clean;
released. After the release the live-site and sign-in checks pass, and
the site's code carries the new screens.
