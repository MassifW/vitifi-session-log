## Backups

**Found by restoring a nightly backup on an Apple-silicon Mac:**

1. A role membership was lost. On live, the role the test harness uses
   to act as a signed-in person (`vitifi_rls_check`) is granted to
   Supabase's `service_role`. The CLI's role dump drops any membership
   whose member is one of Supabase's reserved roles, and the check never
   compared memberships, so a restored copy failed every test-harness
   function while the check passed.
2. Computed values were compared as data. A table of vine-row outlines
   stores its area as a generated column (`st_area`). A restore
   recomputes it, and ARM differs from x86 in the last digits, so the
   row hash differed on the Mac and matched on GitHub's x86 runner.

**The fix.** `extras.sql` now grants each membership involving one of
our roles that the new project lacks (only where missing — creating a
role already makes its creator a member). The fingerprint moves to
**format 2**: it lists memberships (not who granted them), leaves
generated columns out of the row hash (their definitions are still
compared, and every column they are computed from is hashed), and says
which format it is. A format-1 backup is compared the way it was made,
and the check says so. Twelve new tests.

**Verified.** The new SQL first ran against an old local copy, and put
back a revoked membership with the right options, adding nothing on a
second run. Then the nightly workflow on GitHub: passed, with no
failures or warnings. Then that backup restored on the Mac: passed, and
the membership was there with no grant by hand. For the geometry table,
the old all-column hash matches live on x86 and differs on ARM; the new
hash matches on both. The difference was real, and is now excluded
rather than hidden.

## Row-level security

Every read policy was `using (can_read())`. `can_read()` is `SECURITY
DEFINER`, which Postgres never inlines, so it ran once for every row a
query touched. Supabase's documented fix is a scalar subquery, `using
((select can_read()))`, which the planner runs once per statement.

**The migration** reads every policy on public and storage tables (131)
as the database holds it, wraps each role check that is not already
inside a `SELECT`, and alters it — command, roles and permissiveness
untouched. It works from the catalog rather than the original table
lists, because a later table had been added since. It refuses to finish
if anything still asks per row. The one check that needs the row,
`can_write_event(type)`, now takes the two role answers as arguments
through a new `event_write_allowed(type, vineyard, cellar)`, which
`can_write_event()` calls too, so the mapping stays in one place.
`security_surface()` now reports any policy written the old way, and a
test fails on it.

**One risk checked first:** on Supabase, `storage.objects` belongs to
Supabase's storage role, and plain Postgres would refuse to alter its
policies. Supabase's `supautils` extension grants `postgres` policy
rights on that table (checked on live), and the local run altered all
five.

**Measured** on the new backup restored locally, as a vineyard hand
(medians):

    read                          before     after
    provenance of one pick        453 ms     20 ms   (owner: 12 ms)
    a whole-vineyard extent        99 ms    2.2 ms
    counting every vine           164 ms    1.3 ms

The query plan changes from `Filter: can_read()` on every scanned row
to one `InitPlan`, evaluated once.

**Meaning unchanged, shown four ways:** all 131 policies, with the
wrapper undone, are exactly what they were, both locally and on live;
the rewritten event check gives the old answer for 6 roles × 11 event
types, nulls included; the role tests pass unchanged, and so does the
whole suite against the local copy; and the new detector named a
policy put back the old way, in a rolled-back transaction.

**On live:** applied with a dry run first; every test passes against
live, with typecheck and build clean.
